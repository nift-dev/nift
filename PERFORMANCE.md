# Nift rewrite 1.0.7 performance pass

This iteration is the first optimisation-focused replacement-candidate build.
The goal was to recover or beat stripped Nift's 10,000-page performance without
sacrificing the rewrite's simpler architecture, readable JSON implementation,
structured diagnostics, or test coverage.

## What changed

- Parallel incremental analysis for both `build-updated` and `status`.
- Lexical project-relative hash paths instead of filesystem-resolving `relative()` calls.
- Per-pass hash-change caching for shared dependencies.
- Per-pass stored-hash refresh deduplication so shared dependencies are hashed/written once.
- A bounded hash cache so unique per-page dependencies do not inflate memory usage.
- Faster standalone JSON parser:
  - flat object storage instead of `std::map` nodes;
  - fast unescaped-string path;
  - pre-reserved small arrays/objects;
  - line/column calculation moved to the parse-error path;
  - direct string JSON writer/escaping support for hot serialization.
- Streaming `tracked.json` loading so the 10,000-entry JSON DOM is never resident at once.
- Tracking vectors reserve once and move strings from parsed JSON entries.
- Hot page-info serialization writes directly to a reserved string rather than constructing a DOM.
- Repeated filesystem path calculations use lexical operations where paths are already known to be project-owned.
- Raw template/partial source bytes may be cached within a build pass; rendered output is never cached and every page still parses/renders in its own context.
- Shared source buffers have stable ownership without shared_ptr ref-count overhead.
- Chunked plain-text rendering/indentation paths reduce temporary strings and per-character appends.
- Negative `build-threads` multipliers match stripped Nift semantics (`-2` = 2x hardware threads, etc.).

## 10,000-page benchmark

Environment: Linux, 5-core Intel Xeon Platinum 8573C. Both implementations used
the same 10,000-page project and generated byte-identical representative output.
Times below are representative three-run ranges from `/usr/bin/time`.

| Scenario | stripped v0.9 | rewrite 1.0.7 |
|---|---:|---:|
| modified no-op | 0.07–0.09 s | **0.06 s** |
| modified one-page edit | 0.08–0.09 s | **0.06–0.07 s** |
| modified shared partial -> 10k | 0.41–0.61 s | **0.37–0.40 s** |
| modified warm full | 0.32–0.35 s | **0.28–0.33 s** |
| hash no-op | 0.15–0.18 s | **0.09–0.10 s** |
| hash one-page edit, mtime preserved | 0.15–0.16 s | **0.09 s** |
| hash shared partial -> 10k, mtime preserved | 1.09–1.44 s | **0.55–0.68 s** |
| hash warm full | 0.63–1.26 s | **0.47–0.51 s** |

Peak RSS on the rewrite was about 8.0 MB for scans/full builds and about 8.3–8.4 MB
for the 10k fan-out rebuild. Stripped v0.9 used roughly 10.7–12.9 MB for scans/full
builds and 16–18 MB for the fan-out rebuilds in the same benchmark environment.

The rewrite remains built with `-O2` by default. A matching `-O3` build gave only
small/noisy gains and did not justify changing the default optimisation level.
