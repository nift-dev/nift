FINDINGS, ORDERED BY SEVERITY

1. [P2] Newly VM-routed eval admits Error-bearing aggregate presentation that
   terminates internally instead of producing legacy's valid result

Admission route: src/rt/script_runner.cpp:278-299 and the subsequent shared
compile_expression_unit call; src/CLI.cpp:1710-1719.
Underlying serializer: src/rt/natives/format_methods.cpp:54-62, 92-99.

Reproducer:
  NIFT_VM=0       nift eval '[error("x")].stringify()'
  NIFT_VM=require nift eval '[error("x")].stringify()'

Legacy: exit 0, stdout:
  [{"message":"x","code":"user.raised","category":"user","source":"","line":0,"column":0,"cause":null}]
VM: exit 70, no stdout, stderr:
  error: <eval>: NIFT_VM internal failure: unexpected operands (compiler defect): built-in stringify (the script was not run on the legacy engine)

Also reproduced for [error("x")].prettify() and
{"e":error("x")}.highlight(). With
  [print("once"),error("x")].stringify()
both engines print once, but only legacy then produces the JSON result;
the VM terminates internally after that preceding effect.

Both computed-goto and portable switch builds reproduce this. NIFT_VM=1 also
fails internally. Statistics show exactly one VM execution and zero legacy
executions, so this is not a routing-evidence ambiguity.

The serializer's lack of nested Error handling predates CP19, but exposing it
through native eval is a regression of THIS newly selected entry path. The
documented S1 eligibility rule admits compiler-supported lambda-free
expressions, including Error and collection presentation. A successful legacy
expression cannot be counted as an acceptable internal VM failure.

Minimal correction: either correctly support Error values recursively in
these presentation paths, or refuse unsupported combinations before executing
the eval unit. If coverage is deliberately bounded, mode 1 must select legacy
before effects, and require must refuse with zero executions/effects. Do not
replay on legacy after the observed VM failure. Add array/object/nested cases
for all three methods and a preceding-effect control; retain direct Error
presentation and ordinary aggregate formatting.

2. [P2] Collection diagnostics expose synthetic Return context and unsupported
   callback validation through the new eval route

Sources: src/rt/compiler.cpp:230-234 and 385-394;
src/rt/vm_collection_report.cpp:55-58.

Reproducer:
  NIFT_VM=0       nift eval '[1].map(1)'
  NIFT_VM=require nift eval '[1].map(1)'

Both exit 2 with empty stdout. Exact stderr differs:
  legacy: eval: transformation: callback must be callable
  VM:     eval: return: transformation: callback must be callable

filter(true), find(null), sort_by(null), find_index(false) and group_by(null)
exhibit the same synthetic prefix. A multiline expression also reproduces it.
Both dispatches and NIFT_VM=1 are affected; each failure genuinely executes
once on the VM without legacy replay.

compile_expression_unit adds a real Return node. expression_result_ lifts its
scalar-return restriction but does not make its diagnostic context synthetic:
return_statement still attaches kInstrReturnCall to the entire expression.
The existing collection error projector consequently adds "return: ".
This is a direct semantic effect of the new adapter, not merely an existing
VM-versus-legacy message discrepancy. No callback lambda is involved here;
the current compiler admits these malformed-argument expressions as runtime
errors, so the lambda exclusion does not protect them.

There is an additional validation mismatch in this admitted family:
  [1].map("x")
Legacy reports "eval: unknown value or malformed expression: x"; the VM
reports "eval: return: transformation: callback must be callable". Removing
the synthetic prefix alone does not fix that underlying callback-validation
discrepancy. The latter is inherited VM behavior newly exposed by eval, and
is recorded separately as invalid_callback_string in the independent matrix.

Minimal correction: make the synthetic result boundary transparent to return
diagnostic projection. Preserve flags and behavior for actual script/function
return statements; do not globally strip a message prefix. Add exact-message
and multiline-location controls for these admitted collection failures.
Also cover the quoted callback case; match legacy validation or refuse it
before execution rather than silently changing its error contract.
If a callable-method family is instead excluded from S1, enforce that explicit
whole-unit policy before effects and test its accounting honestly.

3. [P2] Nullable Error member access changes eval's existing runtime diagnostic

Sources: src/rt/compiler_error.cpp:28-29, 38-42;
src/rt/vm_ops.cpp:245-251; new eval admission in script_runner.cpp.

Reproducer:
  nift eval 'error("x").cause.message'

NIFT_VM=0: exit 2, empty stdout, stderr:
  eval: cannot access member 'message' because the current JSON value is not an object
NIFT_VM=1/require: exit 2, empty stdout, stderr:
  eval: value has no member: message

The code/source members give the corresponding mismatch too. Both dispatches
show one VM execution and no legacy execution. This is distinct from nullable
Error stringify/prettify/highlight, which remain correct and pass their
12-case regression.

As in finding 1, the underlying generic member behavior predates CP19; the
newly selected eval route exposes it to a command whose exact diagnostic was
previously supplied by legacy. No approved eval diagnostic exception covering
this mismatch was supplied. It is not an Error-origin or synthetic-offset
finding; the demonstrated failure is the public diagnostic text.

Minimal correction: preserve the established nullable member diagnostic or
conservatively refuse the unsupported eval flow before effects. Add present
and absent causes, relevant members and both dispatches. Keep successful Error
metadata access and the separately accepted nullable presentation behavior.

CP18 / CP17 COMPATIBILITY ASSESSMENT

Compared accepted CP18 8f921d7dd6e9ccfc8477238d15749c5d8e9f2f10,
particularly src/embed/program_api.cpp, and accepted CP17 R4
88c5424be1885909a6fd30f717563e56d50c1175 and its VM/compiler/handle interfaces.

CP18's program owns bytecode and SourceMap. Its run API leaves the new result
pointer null, so it continues to own copied output, returned_text and error
strings independently of program lifetime. CP19's data Value capture uses the
existing refcount/COW model and converts while Program/VM/SourceMap are alive.
The two entry points have different explicit result representations, not two
new lifetime implementations. No public C ABI layout changed here. Callable
Values still depend on Program lifetime; the eval lambda exclusion must remain
until that ownership contract is implemented deliberately.

CP17's one-table/context-per-run and W13 checks must survive integration.
Expression compilation must not bypass its handle-flow pass: a handle result
or an aggregate containing handles must refuse before effects rather than
reach the legacy result bridge. The current bridge deliberately has no generic
typed-handle conversion. Error origins and caller-owned resources must survive
exceptions on the actual combined runtime.
