# v4.6 Batch 4 recoverable operational errors: design checkpoint

Status: **DESIGN ONLY - implementation requires a separate human approval.**

This checkpoint does not add `try`, `catch`, `throw`, an Error value, or any
new catchable operation. It freezes a proposed contract after auditing the
current evaluator, operational APIs, workers, resources, imports, embedding
surface, and tests.

## 1. Objective and non-objective

The objective is to let library-style operational failures propagate to a
caller that deliberately handles them. It is not to turn every Nift failure
into an exception.

The core distinction is:

```text
recoverable operational failure
    external or explicitly raised failure that the current program may
    reasonably handle and continue from

programmer, language, invariant, or policy failure
    malformed program or invalid runtime use for which local recovery would
    hide a defect, violate an authority boundary, or continue from an
    untrusted state
```

An uncaught recoverable error remains a controlled top-level script/render
failure. Existing programs that do not use `try` should therefore retain their
current exit behavior and approximately the same diagnostic text.

The design does not promise rollback of arbitrary side effects. Catching a
failure is control-flow recovery, not a transaction.

## 2. Current implementation evidence

Nift currently has several overlapping failure channels:

- Expression and native operations predominantly return `bool` plus
  `std::string& error` (`Parser.h`, `ParserExpression.cpp`).
- Template failures mutate a parser-owned `RenderResult`; `Parser::fail()`
  computes source, line, column, span, source line, and message
  (`Parser.cpp:691-727`, `Types.h:46-75`).
- `return`, `break`, and `continue` use parser-global `pending_control_`
  (`Parser.h:374-384`).
- Prepared AST dispatch uses `false` plus an empty error to mean "unsupported,
  use the legacy evaluator", while `false` plus a non-empty error means failure
  (`Ast.cpp:107-118`).
- Functions, methods, lambdas, callbacks, and imports commonly reduce a nested
  `BuildError` to its message (`ParserExpression.cpp:1983-2019,2352-2417,
  3275-3300`; `ParserScript.cpp:478-484`).
- Futures and threads store only a value or error string; `await` and `join`
  add presentation prefixes (`Parser.h:240-274`,
  `ParserExpression.cpp:1183-1207,1334-1355,1768-1777`).
- `execute_native_program()` catches C++ exceptions as a last-resort boundary
  and converts `what()` to a diagnostic (`ParserScript.cpp:366-390`).
- Public `RenderError` has message/source/line/column, but embedded script paths
  often flatten failures and replace their source with `<embed>`
  (`render_error.h:11-17`, `Engine.cpp:326-376`).

Important consequences:

1. Empty error strings, operational failures, abrupt control, and internal
   exceptions cannot remain overlapping channels after catchability is added.
2. A catchable failure must preserve its origin through call, import, and
   worker boundaries instead of reconstructing a new diagnostic at each caller.
3. Expected Nift failures must not be implemented by throwing arbitrary C++
   exceptions through the evaluator.
4. Prepared and legacy execution need one semantic outcome model even while
   their parsers remain separate.

## 3. Recommended syntax

### 3.1 Catch and explicit propagation

```nift
try {
    value := load()
} catch(err) {
    print(err.message)
}
```

```nift
throw error("configuration is missing", "user.config.not_found")
```

```nift
try {
    operation()
} catch(err) {
    cleanup()
    throw err
}
```

The recommendation is `throw`, not `raise` and not a bare `error(...)` that
implicitly transfers control.

- `throw` fits Nift's brace-based, C-like `if`/`while`/`return` grammar.
- It makes non-local control visible at the statement site.
- It pairs naturally with `try`/`catch`.
- `raise` would introduce Python vocabulary beside `catch`.
- Making `error(...)` itself raise would disguise control flow as a normal call
  and would be especially confusing beside existing `err(...)`, which writes
  to stderr and does not report failure.

`error(message[, code[, cause]])` is a constructor for an Error value; it does
not throw. The compatibility cost is explicit: `error` is currently a valid
callable name. The audit confirmed that `error`, `try`, `catch`, and `throw` are
all currently legal identifiers, and that user/module/first-class callables take
precedence over native builtins. That precedence is retained: a user-defined
`error(...)` shadows the constructor in its scope. The repository and sibling
package `.f` sources currently contain no such declarations/calls, but the
language compatibility rule does not depend on that absence.

The contextual grammar is:

```text
try-statement   := "try" block "catch" "(" identifier ")" block
throw-statement := "throw" whitespace expression statement-end
```

`try(...)`, `throw(...)`, member calls such as `obj.throw(...)`, assignments to
those names, and declarations using those names retain their existing meaning.
The `throw` statement deliberately requires whitespace, so an existing
statement-position `throw(value)` call is not stolen. `catch` is special only as
the required continuation parsed by a `try` statement. A malformed `try` shape
is a syntax error rather than a fallback to a callable. CP1 must pin these forms
and search package usage before parser work starts.

### 3.2 Grammar limits for v1

- `try` and `throw` are function-program/script statements, alongside
  `if`, `while`, and `return`.
- They are available in standalone scripts, `@script`, function bodies,
  methods, and block lambdas that use function-program grammar.
- No new `@try`, `@catch`, or `@throw` template directives are added.
- A template can call a function that handles an error, and an uncaught error
  from a template expression still fails the render.
- `try` must have exactly one `catch(identifier)` and both require braces.
- There are no typed catches, filters, multiple catches, catch guards, or
  optional catch binding in v1.
- `throw` requires an Error expression. There is no arbitrary-value throwing
  and no bare `throw`; rethrow is `throw err`.
- The new words are contextual, not globally forbidden as member names or
  identifiers outside the exact productions above.

## 4. Error value model

### 4.1 Dedicated, inspectable runtime value

Use a dedicated internal `RuntimeType::Error`, appended to the existing enum so
existing type ordinals and fingerprints do not change. It is an ordinary
language value in the sense that caught code can bind it, inspect it with member
access, pass it to another Nift function, store it in data structures, return it
to Nift callers, copy it, and explicitly throw it again. It is not an ordinary
object and cannot be forged by JSON or by constructing an object with similarly
named fields.

The v1 public fields are:

```text
message   mandatory string
code      mandatory machine-readable string
category  machine-readable string derived from the code prefix
source    logical source/path string, or "" when unavailable
line      1-based integer, or 0 when unavailable
column    1-based integer, or 0 when unavailable
cause     Error or null
```

Rules:

- `message` is diagnostic text and is not a stable matching contract.
- Built-in `code` values are stable API once published.
- `category` is the segment before the first `.` in `code`.
- The categories `io`, `stream`, `process`, `json`, `schema`, `package`,
  `network`, `database`, `native`, `ffi`, `host`, `policy`, and `internal` are
  reserved to Nift. The public constructor accepts only `user.*` custom codes;
  packages use `user.<owner>.<code>`. Their stability belongs to the defining
  library, not Nift. User code cannot impersonate a built-in or fatal code.
- A custom code has 2-8 dot-separated segments, begins with `user`, is at most
  128 ASCII bytes, and each segment matches `[a-z][a-z0-9_-]{0,31}`. Empty
  segments and uppercase/non-ASCII spellings are rejected as fatal constructor
  misuse.
- Disposition is never inferred from a user-supplied code. `error(...)` can
  construct only `user.*` codes. `throw` accepts any genuine Error, including a
  caught built-in Error, and propagates its code unchanged as a recoverable
  failure.
- `error(message)` defaults to `user.raised`.
- `error(message, code)` validates the code and derives the category.
- `error(message, code, cause)` requires `cause` to be Error or null.
- Source fields are trusted origin metadata. The constructor does not accept
  them. Throwing an Error without origin creates a new enriched immutable Error;
  it never mutates the original value or aliases. Rethrowing an Error that
  already has origin preserves it.
- A valid origin has a non-empty logical source and nonzero line and column.
  Otherwise all three fields are replaced together from the `throw` keyword's
  location; if that source has no location, they remain `""`, `0`, `0`. The
  private diagnostic span covers the full throw statement and snapshots its
  source line. Constructing or storing an Error does not assign origin.
- Error fields are immutable. The catch binding is also immutable, though a
  programmer may create a different local binding.
- `cause` is only Error/null in v1. Arbitrary payloads are deferred, avoiding
  resource handles, callables, timers, and parser-owned identities hidden in an
  error graph.
- Cause depth is limited to 16 Error values including the root. Exceeding that
  limit is fatal constructor misuse. Public immutable constructor-only causes
  cannot form cycles, but internal copy/adapter code must still reject cycles
  defensively. The limit applies to construction, `stringify`/`prettify`, worker
  transfer, diagnostic projection, equality, and public-boundary rejection.

This is a dedicated value rather than a magic object because catch
discrimination and trusted origin data must not be forgeable through ordinary
JSON. It remains deliberately much smaller than an exception-class hierarchy.

### 4.2 Value behavior

- `type(err)` returns `"error"`.
- Error truthiness is `true`.
- Normal member access reads the seven public fields above.
- Equality is structural over all public fields and the cause chain. There is
  no hidden exception identity.
- Error is immutable, so `copy()` may share immutable backing and `deepcopy()`
  produces the same observable value. Origin enrichment returns a new value, so
  previously stored aliases remain unchanged. Internal propagation frames are
  carried by Failure, are not Error fields, and do not affect equality,
  copying, or stringification.
- Direct template rendering and implicit scalar interpolation reject Error,
  just as other non-renderable runtime values do. Code should render
  `err.message` deliberately.
- `stringify()` and `prettify()` produce a canonical Nift object-shaped
  representation in field order `message`, `code`, `category`, `source`,
  `line`, `column`, `cause`, using existing string escaping and integer spelling;
  null cause is explicit. This stable diagnostic representation is not accepted
  as strict JSON input for Error.
- Strict JSON conversion rejects Error in v1. JSON cannot synthesize Error.
- A function may return an Error as a normal language value. A successful value
  graph containing Error at any depth may not cross the public C++/C/binding
  boundary in v1. Direct Error and Error nested in an array, object, collection,
  or struct are recursively rejected with a controlled unsupported-value
  failure, like other interpreter-only resources.

The last restriction avoids redesigning public `Value`, JSON result transport,
and all bindings during this checkpoint. It does not affect caught errors or
uncaught error diagnostics.

## 5. Catchable taxonomy

Catchability is attached to a structured diagnostic disposition, not inferred
from message text or category alone. `try` catches only `Recoverable` failures.
`Fatal` failures propagate past every language catch to the existing top-level
diagnostic boundary.

### 5.1 Recoverable in v1

- Explicit `throw` of an Error.
- Filesystem failures caused by external state after valid arguments and
  authority checks: missing/unreadable paths, permission failures, I/O errors,
  failed create/copy/move/remove, and failed atomic save/replace.
- Input/output stream backend failures after a valid live stream operation.
- Runtime data parsing failures, such as malformed JSON supplied to a library
  parse/inject operation.
- Validation rejection of a candidate by a valid schema.
- FFI library load failure and symbol-not-found after valid argument/signature
  checks.
- Missing/unreadable import sources, including an uninstalled bare package,
  only after import rollback completes and only when metadata/schema,
  provenance, and authority checks did not fail.
- A recoverable error produced inside a future/thread, observed at `await` or
  `join`.

This list is exhaustive for automatic v1 conversion. Process result APIs,
package transaction commands, host callbacks/providers, networking/database
wrappers, and native-tool wrappers remain on their current result/fatal channels
unless Nift code explicitly throws a `user.*` Error.

### 5.2 Not catchable in v1

- Syntax errors, incomplete/malformed language constructs, and translation
  errors.
- Unknown bindings/callables/members caused by program text.
- Invalid arity, type, mode, index, mutability, control placement, or unsupported
  operation caused by programmer use.
- Division by zero, arithmetic domain/range errors, and recursion/depth limits.
- Privacy/export violations and invalid package manifests or lock schemas.
- Project/package/filesystem authority denials, restricted-mode denials,
  traversal rejection, and containment failure.
- Stale package provenance, forged/stale/closed internal handles, timer-owner
  mismatch, and resource-transfer violations.
- Post-journal package transaction failures or any state requiring explicit
  repair/recovery.
- Broken interpreter invariants and unexpected C++ exceptions.
- Existing host loader/environment `Error` results and host-callable exceptions.
  The current public seams cannot distinguish operational failure from a host
  policy denial without an API redesign, so they remain fatal in v1.
- Native crashes, signals, access violations, memory corruption, ABI mismatch,
  allocation failure, or arbitrary foreign exceptions.

Security and policy failures are intentionally fatal even though a caller might
wish to continue. Catching them would let code probe or suppress an authority
boundary and is not enabled without a separate API-level design.

### 5.3 Existing result APIs remain results

The following do not automatically raise:

- A launched process returning nonzero.
- `run()`/`cmd().run()` structured process outcomes.
- Parent-side process spawn/capture/wait failures reported through those result
  APIs. Direct command statements retain their current uncaught failure behavior
  in v1; callers that need recovery should use a result API and explicitly
  throw.
- HTTP, database, Redis, image-tool, and similar package objects returning
  `{ok:false,...}`.
- Build/automation APIs that already return structured operation results.
- `exists()` returning false.

Library authors may inspect those values and explicitly construct/throw an
Error. This prevents a broad behavioral change and keeps domain-specific result
handling available.

Before CP4, an independently reviewed registry must map every automatically
catchable branch to code, category, origin selection, compatibility message, and

contract. Platform details may be included in diagnostic text or a future
non-stable details field.

Initial Nift-owned categories are `io`, `stream`, `json`, `schema`, `package`,
and `ffi`. `process`, `network`, `database`, `native`, and `host` are reserved
for later Nift use but have no automatically catchable v1 branches. `policy` and
`internal` diagnostics exist internally but are never catchable.

## 7. Propagation semantics

### 7.1 General

- The nearest dynamically enclosing `try` catches a `Recoverable` failure from
  its try body.
- Fatal failures bypass catches unchanged.
- Catch creates a child lexical scope containing one immutable Error binding.
- Normal fallthrough from the try skips catch.
- A recoverable failure in catch propagates to an outer try.
- `throw err` preserves the original source and cause; the rethrow site is an
  internal propagation frame, not a replacement origin.
- `return`, `break`, and `continue` are not errors. They propagate through try
  and catch according to existing function/loop boundaries.
- Catch does not intercept `return`, `break`, or `continue`.

### 7.2 Functions, methods, lambdas, and callbacks

Recoverable errors cross ordinary callable boundaries without conversion to a
new message. The original Error is preserved and the runtime may append internal
context frames for diagnostics. Named functions, methods, block lambdas,
and Nift collection callbacks use the same outcome channel. Existing host
callbacks remain fatal in v1 because their public API cannot carry the required
recoverable disposition safely.

Expression lambdas cannot contain statement-level try/catch unless their body
grammar is expanded separately. They may call a function that catches or may
propagate a recoverable operation failure to an enclosing statement-level try.

### 7.3 Imports and modules

- A module can catch its own recoverable failures.
- An uncaught recoverable error crosses the import boundary only after the
  existing import rollback has removed uncommitted module environments,
  callables, lambdas, structs, files, prepared-callable entries, and identity
  allocations.
- An importing try may catch a recoverable import failure.
- No partial exports are installed on failure.
- The Error origin remains the defining imported source. The import site is a
  context frame, not a replacement source location.
- Syntax, export/privacy, manifest, provenance, and containment errors remain
  fatal and cannot be hidden by import catch.
- Import rollback currently does not own every parser resource registry. Before
  explicit throw is allowed to escape an import, the checkpoint must track every
  registry entry and identity allocation created by the module: futures, threads,
  mutexes, atomics, timers, streams, FileValues, FFI libraries, buffers,
  callbacks and pointers, collections, command instances, lambdas, structs,
  modules, and prepared entries. Parser-local counters may be restored; shared
  process-global monotonic IDs remain consumed and are never rewound.
- A failed import that created any future or thread is deterministically fatal,
  regardless of whether the worker happened to finish before failure was
  observed. It produces `internal.import_lifecycle`, bypasses catch, and keeps
  the complete ownership domain parser-owned until existing top-level worker
  finalization has joined/drained it; cleanup and graph rollback run only after
  that finalization. No worker is detached and its host, tracked source, module,
  and parser references remain alive. A nonterminating worker may therefore
  retain the current blocking top-level teardown behavior; cancellation and a
  nonblocking lifetime redesign are explicitly outside v1.
- A failed import without workers is recoverable only when every created resource
  has a registry-specific, nonblocking and safe cleanup rule in the CP1 ownership
  matrix. Cleanup and graph rollback finish before catch. Otherwise it is the
  same fatal lifecycle failure and remains parser-owned until safe teardown.
  External side effects already performed by a worker are not undone.

### 7.4 Templates, scripts, and REPL

- Uncaught recoverable errors fail a template/script through the same controlled
  top-level result used today.
- Direct template grammar does not gain try/catch in v1.
- `@script` and function-program bodies may use try/catch.
- The REPL reports an uncaught error and remains usable, as it does for current
  controlled errors.
- A caught error permits later statements in the same command to run.
- A try block is not a state transaction. Bindings and external side effects
  completed before the failure retain their ordinary semantics unless an
  existing operation checkpoint already rolls them back.

## 8. Async and thread behavior

Workers must store a structured completion, not separate `result` and error
strings:

```text
Pending | Value | Recoverable(Error) | Fatal(Diagnostic)
```

- A worker recoverable failure remains latent until `await` or `join`.
- `await`/`join` replays it in the observing parser. A surrounding try at that
  point may catch it.
- The Error keeps the worker source/line/column. Await/join add diagnostic
  context without changing origin.
- A fatal worker failure is replayed at await/join but bypasses catch.
- Repeated observation must replay the same value or failure consistently.
- Existing nested-worker progress and no-starvation behavior remains unchanged.
- Worker boundaries still catch unexpected C++ exceptions and classify them as
  fatal internal diagnostics. Resource exhaustion such as `std::bad_alloc` is
  outside the recovery guarantee unless an allocation-free emergency completion
  path is separately proven.
- Errors may not carry worker-owned timers, handles, callables, files, mutexes,
  futures, threads, FFI pointers, or mutable parser state.
- Unobserved worker failures retain current teardown behavior in v1; changing
  them into destructor-time errors is deferred because that would alter program
  success based on observation policy.

## 9. Cleanup and resource implications

No `finally` is added in v1.

Existing C++ ownership/RAII boundaries must release package locks, filesystem
transactions, temporary native buffers, and worker synchronization state before
a failure is made visible to catch. This is implementation cleanup, not new
language magic.

Language-visible rules:

- Catching does not undo successful writes, saves, copies, moves, removals,
  process launches, network requests, database changes, or output already sent.
- A failed managed-file save leaves a FileValue that survives the current
  operation/call checkpoint open and dirty, allowing retry/revert. Uncaught
  top-level script/embed failure still runs existing final cleanup, and a broad
  callable/import checkpoint may discard a FileValue created inside that
  boundary before an outer catch sees the failure. CP1 freezes each checkpoint
  owner before this becomes a public promise.
- Newly created FileValues/timers follow their existing operation checkpoint
  rules. Catching must not cause rollback to run twice or delete resources that
  existed before the failing operation.
- A resource remains the caller's responsibility after catch only if it predates
  the rollback checkpoint that owns the failure, or otherwise survives that
  checkpoint. A resource created earlier in a broad callable/import operation
  may still be invalidated by that operation's existing rollback, even if a
  caller aggregate briefly received its handle.
- Locks and package read transactions may not remain held while catch code runs.
- Import rollback completes before an importer catch executes.

Without `finally`, a library that must clean up on both success and failure can
use a helper boundary and an explicit catch-cleanup-rethrow pattern. The current
package wrappers that create temporary files and then call another potentially
failing operation need review before their failures are converted automatically.
If real usage demonstrates unacceptable duplication, `finally` receives a
separate design checkpoint; it is not smuggled into v1.

## 10. Embedding and C ABI

No embedding ABI redesign is part of v1.

- A caught error is ordinary internal script control flow and is invisible to
  the host unless script code deliberately returns derived ordinary data.
- An uncaught recoverable error maps to the existing failed `ScriptResult` or
  `RenderResult`.
- Existing captured stdout/stderr remains available on failure.
- Existing C ABI calls continue returning mechanical status separately from a
  semantic failed result. An uncaught language error is not
  `NIFT_ERROR_INTERNAL`.
- Existing projection remains the compatibility surface: C++ ScriptResult and
  RenderResult carry `RenderError`; C ABI render results expose
  message/source/line/column; C ABI script results expose only message. Script
  paths should stop losing source internally, but no new C ABI accessor is
  promised in v1.
- Public C++ result classes contain `RenderError` by value, so adding fields
  would change class layout. This design does not do that.
- Error is initially interpreter-only and is not added to public `Value::Type`.
- Successful value graphs containing Error anywhere recursively are rejected as
  unsupported rather than silently encoded as JSON.

An additive future ABI checkpoint may expose stable codes/causes through opaque
result accessors and a C ABI minor version. That is not required for language
catch semantics and must be reviewed independently.

### 10.1 Uncaught compatibility matrix

| Surface | v1 compatibility rule |
|---|---|
| CLI exit/nonzero result | Exact current success/failure class |
| C ABI mechanical status | Exact; semantic language failure remains a result, not `NIFT_ERROR_INTERNAL` |
| Existing diagnostic message | Exact for characterized legacy failures; explicit new errors use their supplied message |
| Source/line/column | Intentionally corrected to original source where currently flattened; correction must be documented per test |
| Captured stdout/stderr | Exact bytes retained before failure |
| Import/future/thread prefixes | Exact flattened compatibility message even when internal frames become structured |
| Existing result fields | Exact presence/types; no layout change |
| Error code/cause | Internal-only and non-ABI in v1 |

## 11. FFI boundary

Only failures already detected safely by Nift are candidates:

- library load failure;
- symbol not found;
- a future explicitly supported native result convention.

Library unload failure is deferred because current lifecycle/handle state does
not provide a reviewed retry contract.

Bad signatures, arity/type errors, invalid pointer/library handles, callback
contract violations, and nested callback misuse remain fatal programmer errors.
Signals, crashes, access violations, memory corruption, and arbitrary foreign
exceptions are never catchable. Nift must not imply that `try` is a native fault
sandbox.

## 12. Proposed internal architecture

### 12.1 One structured diagnostic

Use discriminated failure forms rather than an independently stored disposition
and optional value:

```text
RecoverableFailure {
    error: Error                 # mandatory
    origin span/source line      # diagnostic-only detail
    propagation frames
}

FatalFailure {
    code/category
    message
    origin source/span/line/column
    propagation frames
}
```

Every recoverable operation constructs an Error before propagation. It is
impossible to represent a recoverable failure without the value required by
`catch`. Trusted source span/source-line detail and propagation frames remain in
the Failure wrapper; they are not mutable public Error fields and are preserved
when a caught Error is rethrown only to the extent represented by its immutable
public origin/cause. Rethrow creates a new wrapper around that Error and a new
frame; it does not resurrect discarded private frames from an earlier caught
wrapper.

Display formatting adapts this diagnostic into existing `BuildError`,
`RenderError`, CLI text, and worker reporting at outer boundaries. Message-prefix
tests such as recursion/import/future/thread classification must no longer drive
semantics.

### 12.2 Explicit expression and statement outcomes

Replace ambiguous boolean channels incrementally with:

```text
EvalOutcome<T> = Value(T) | Unsupported
               | RecoverableFailure(Error, frames)
               | FatalFailure(Diagnostic)

ExecOutcome = Normal
            | Return(value, optional location reference)
            | Break
            | Continue
            | RecoverableFailure(Error, frames)
            | FatalFailure(Diagnostic)
```

`Unsupported` exists only for prepared-to-legacy capability fallback. It is not
a runtime error.

The return payload must preserve the current root/path location identity used by
location-returning functions. Loops consume only break/continue; callables
consume only return; try consumes only recoverable failure.

### 12.3 Do not use C++ exceptions for Nift control flow

Do not implement `throw` by throwing a C++ object through the evaluator. Do not
add `Throw` to parser-global `pending_control_` as the final architecture.

Use explicit outcomes and local execution frames. RAII guards may restore C++
scope/module/resource state, but destructors do not transport language errors.
C++ catches remain at foreign callback, worker entry, public Engine, and C ABI
boundaries solely to contain unexpected native exceptions as fatal internal
diagnostics.

### 12.4 Legacy and prepared paths

Prepared dispatch should first adopt `Value | Unsupported | Failure`, eliminating
the empty-string fallback convention. Prepared statements then adopt explicit
`ExecOutcome`. Legacy scanner/directive handlers receive adapters and are
converted checkpoint by checkpoint. Both paths must call the same Error
constructor, try/catch executor, operation classifier, and diagnostic formatter.

Full template-AST migration is not a prerequisite. The active scanner can
return explicit outcomes while preserving source offsets.

## 15. Explicit v1 deferrals

- `finally`, `defer`, or language-level RAII.
- Typed/category catches, multiple catches, filters, and exception classes.
- Arbitrary thrown values or arbitrary Error payloads.
- Automatic conversion of `{ok:false}` package/process/database/network results.
- Automatic conversion of host provider/callable failures, direct command
  failures, or CLI package transaction failures.
- A new typed/versioned host-callable failure API.
- Catchable syntax/type/arity/privacy/arithmetic/policy/invariant failures.
- Catching native crashes, signals, memory faults, or arbitrary FFI exceptions.
- Cancellation semantics for futures, threads, processes, or network requests.
- Automatic rollback of filesystem/network/database/process side effects.
- Platform-exhaustive `errno`/Win32 code exposure.
- Successful Error transport through public `Value`, C ABI JSON, or bindings.
- Public ABI fields for error code/category/cause.
- Direct template `@try`/`@catch` syntax.
- Changing unobserved worker-failure teardown behavior.

## 16. Approval questions

Human review should explicitly decide:

1. Approve `throw error(...)` versus another explicit constructor/spelling.
2. Approve a dedicated immutable Error runtime type rather than ordinary object.
3. Approve the fatal/recoverable classifications in sections 5 and 6.
4. Approve keeping existing structured-result APIs non-throwing.
5. Approve catch-at-`await`/`join` worker semantics.
6. Approve no `finally` in v1.
7. Approve interpreter-only Error with no public ABI redesign.
8. Approve explicit outcomes rather than C++ exception unwinding or a final
   parser-global `Throw` state.

Implementation remains blocked until those questions receive human approval.
