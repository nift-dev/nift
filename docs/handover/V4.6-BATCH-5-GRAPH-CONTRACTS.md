# V4.6 Batch 5 — graph identity and lock contracts (design clarification)

Companion to `V4.6-BATCH-5-DEPENDENCY-GRAPH-DESIGN.md` (the campaign
audit/checkpoint plan). This pins the contracts that must be exact before the
v2 lock format is frozen and before CP10. No implementation.

## 1. Node identity vs edge requirements

A graph lock must distinguish the **resolved package node** from the
**requirement edges** that caused that node to be selected. A single per-node
`requested` cannot faithfully represent two parents requesting the same
package differently.

### Exact v2 JSON schema

```json
{
  "lockfileVersion": 2,
  "packages": {
    "<package-name>": {
      "source": "<canonical/resolved source identity>",
      "commit": "<40/64-hex exact git commit> | \"local\"",
      "requirements": {
        "<child-package-name>": {
          "source": "<requirement source spelling>",
          "requested": "<requirement ref>"
        }
      }
    }
  }
}
```

Semantics:

- `packages` is keyed by **package name** (the graph identity; one node per
  name — see section 2). Keys serialize in sorted order.
- Each node's `source` is the **canonical/resolved source identity** (section
  3) and `commit` is the exact pinned revision (or `"local"`).
- Each node's `requirements` records **that package's own declared
  dependencies as edges**: per child, the **requirement spelling** (`source`)
  and **requested ref** (`requested`) exactly as declared in that package's
  manifest. Edge requirements are **not** replaced by the child's canonical
  source or resolved commit.
- Root requirements are **not** repeated in the lock; they live in
  `manifest.json`. Package-to-package requirements have full fidelity in the
  lock via `requirements`.

Validation rules (CP10):

- `lockfileVersion` must be the number `2`.
- Every `packages` key is a valid package name; every node has a safe-string
  `source`, a valid `commit` (`exact_commit` hex or `"local"`), and a
  `requirements` object.
- Every `requirements` key is a valid package name; every edge has safe-string
  `source` and `requested`.
- Every child named in any `requirements` edge must have a corresponding node
  in `packages` (the closure is closed under edges).
- Deterministic serialization: `lockfileVersion`, then `packages` with sorted
  keys and sorted `requirements` keys, compact JSON.

This answers, from the lock alone (plus root `manifest.json`):

```text
why is b present?          -> some node's requirements edge names "b"
which parents require b?   -> every node (and the root manifest) whose
                              requirements/manifest names "b"
what source/ref did each parent request? -> the edge {source, requested}
what exact commit satisfied them?        -> b's node {source, commit}
```

## 2. Package name is the primary graph identity

- The installed store is `.nift/packages/<name>`, and package manifests
  already declare/validate their own `name`. Therefore **one resolved node per
  package name**.
- All requirements targeting a name (root manifest entry plus every package
  node edge naming it) are **collected** and checked for compatibility. Do not
  create two nodes for the same name because requirement strings differ. Do
  not merge two differently named packages because they share a source/ref.

Compatibility (explicit):

```text
same name + same canonical source + same resolved commit  -> compatible, shared node
same name + different canonical source                    -> conflict (fatal)
same name + same source + different resolved commit        -> conflict (fatal)
```

- Different **requested refs** that resolve to the **same exact commit** are
  **compatible**: one node, both edge requirements recorded. This is an
  explicit contract.
- Different refs that resolve to **different commits** are a conflict
  (fatal), because v1 installs one version per name.

## 3. Source identity / canonicalization

Current source spellings produced by `package_git_source`:

```text
registry shorthand   "b"                  -> https://github.com/nift-packages/b.git
GitHub shorthand     "github:o/r"         -> https://github.com/o/r[.git]
HTTPS git URL        "https://..."        -> as-is
SSH git URL          "git@host:path"      -> as-is
file:// URL          "file://..."         -> as-is (git URL)
absolute local path  "/x/y"               -> local
relative local path  "./x", "../x", "x/y" -> local (resolved per section 4)
```

Contract:

- **Canonical source identity** for a Git requirement is the exact string
  `package_git_source(source)` — the URL the resolver actually clones.
- **Equality for graph conflict detection** compares canonical source strings
  **exactly** (string equality). No fuzzy URL equivalence is invented: e.g.
  `git@github.com:x/y.git` and `https://github.com/x/y.git` are treated as
  **different** sources even though they may denote the same remote. This is
  deterministic and safe.
- **Local** canonical identity is the resolved absolute normalized path
  (section 4); local paths are inherently machine-specific (section 5).
- The **lockfile representation** stores the canonical source on the node and
  the requirement spelling on the edge, so both the resolved identity and the
  original requirement are preserved.

## 4. Relative local dependency semantics

- A `local` relative `source` declared in a **package** manifest resolves
  **relative to the directory containing that package manifest** (the package
  root), not the consumer-project CWD, process CWD, or root manifest.
  E.g. `/packages/a/manifest.json` with `{"b": {"source": "../b",
  "ref": "local"}}` resolves to `/packages/b`.
- `../sibling-package` is **permitted** as an acquisition source. This is
  package **acquisition**, distinct from `module_path()`/`package_path()`
  resource confinement; runtime package-root traversal policy is not applied
  to dependency-source resolution without a deliberate reason. (The store
  confinement `.nift/packages/<name>` applies to where the package is
  **installed**, not where it is fetched from.)
- The earlier exploratory fixture used `./b` with `a`/`b` as siblings; that
  fixture only proved the current resolver ignores the dependency. Resolver
  tests must use path topology matching this contract.

## 5. Reproducibility guarantee for `local`

- Git/remote dependencies: **content reproducible by exact commit** (detached
  checkout, verified).
- Local dependencies (`commit == "local"`): **graph/path resolution is
  deterministic**, but **contents intentionally track the local source**
  (live). There is **no content digest** in v1; a stronger local-content
  reproducibility guarantee is a separate future feature, not claimed here.
- The campaign does **not** claim "the complete graph is exactly reproducible
  across machines" for local dependencies — only for the graph structure and
  Git-pinned contents.

## 6. Floating refs resolve once per transaction

- Within one resolver transaction, memoize `(canonical source, requested ref)
  -> exact resolved commit`. A moving remote ref is resolved once; every
  parent sharing that requirement observes the same commit.
- The resulting lock is the authority for ordinary `install`: `install` with a
  valid exact lock **does not re-resolve** floating refs.
- `update` is the only operation that deliberately re-resolves floating
  requirements.

## 7. Targeted update semantics

- `nift update <name>` is restricted to a **root/direct dependency** for v1;
  naming a transitive package is a clear error.
- Behavior:
  - Re-resolve `<name>` and its **reachable closure** to new commits.
  - Preserve unrelated root packages at their locked commits.
  - After re-resolution, recompute **shared-node compatibility globally**.
  - If the refreshed closure conflicts with a still-pinned requirement, the
    command **fails atomically** (no partial manifest/lock/store) with a
    conflict error naming both dependency paths.

Worked rule for `root -> a -> b` and `root -> c -> b`: updating `a` such that
its `b` requirement now resolves to a different commit than pinned `c`'s
requirement → conflict → deterministic atomic failure, no change applied.

## 8. v1 -> v2 migration

- **Read-only/runtime operations** (imports, `module_path`, `package_path`,
  provenance checks): accept valid v1 locks, **do not rewrite** them.
- **First successful package-mutating operation** after graph support
  (`add`/`install`/`update`/`remove`): resolve the closure and **atomically
  emit v2**.
- **No half-v2 state:** the CLI is not left writing a graph-shaped lock it
  does not understand. CP10 lands v2 parse/validate + internal
  graph-capable representation + deterministic v2 serialize, but does **not**
  change what commands emit; commands continue to read/write v1 until CP12
  wires the resolver and flips emission to v2 in one change. (CP10's "no
  resolver change" is exactly this: schema + representation + round-trip only.)
- CP10 accepts valid v1, accepts valid v2, validates each per its schema,
  exposes the internal graph representation, and serializes v2
  deterministically — without silently rewriting user locks on read.

## 9. Package-manager failures vs Batch 4 runtime recoverables

Batch 4 left package transaction commands on their existing result/fatal
channels. Batch 5 does **not** expand the recoverable boundary.

```text
CLI graph acquisition/resolution/fetch failure
    (nift add/install/update/remove while resolving/fetching)
    -> package command failure + transaction rollback (fatal command outcome,
       NOT a catchable Nift Error)

later script runtime import of a missing installed package
    -> package.not_installed  (recoverable, Batch 4)

installed package entry/source disappears or becomes unreadable at runtime
    -> package.import_source_unreadable  (recoverable, Batch 4)

malformed manifests/locks, graph conflicts, graph cycles
    -> fatal command/configuration failures (never catchable via Batch 5)
```

`package.manifest_invalid` / `package.lock_invalid` stay fatal
configuration failures. A resolve-time malformed transitive manifest is a
fatal acquisition error with transaction rollback.

## 10. Graph query data source

- The CP13 "why is this installed / which path requires it" query must be
  answered from **root `manifest.json` requirements + the v2 lock edges
  alone** — never by opening installed packages on disk.
- Traversing root manifest requirements plus each node's `requirements` must
  reconstruct every root-to-node requirement path deterministically. This is
  used as a schema completeness test during CP10's review.

## Worked graph

Graph:

```text
root
├── a@X
│   ├── b@Y
│   └── d@Z
└── c@W
    └── b@Y        (c requests b@v1.2.3; a requests b@latest; both -> Y)
```

Root `manifest.json`:

```json
{"dependencies": {"a": {"source": "github:org/a", "ref": "latest"},
                  "c": {"source": "github:org/c", "ref": "latest"}}}
```

`a/manifest.json`:

```json
{"name": "a", "version": "1.0.0", "entry": "src/a.f",
 "dependencies": {"b": {"source": "github:org/b", "ref": "latest"},
                  "d": {"source": "github:org/d", "ref": "latest"}}}
```

`c/manifest.json`:

```json
{"name": "c", "version": "1.0.0", "entry": "src/c.f",
 "dependencies": {"b": {"source": "github:org/b", "ref": "v1.2.3"}}}
```

`b`/`d` manifests declare `name`/`version`/`entry` and no dependencies.

Resulting v2 lock (edge requirements preserved; `b` is one shared node):

```json
{
  "lockfileVersion": 2,
  "packages": {
    "a": {
      "source": "https://github.com/org/a.git",
      "commit": "X...",
      "requirements": {
        "b": {"source": "github:org/b", "requested": "latest"},
        "d": {"source": "github:org/d", "requested": "latest"}
      }
    },
    "b": {
      "source": "https://github.com/org/b.git",
      "commit": "Y...",
      "requirements": {}
    },
    "c": {
      "source": "https://github.com/org/c.git",
      "commit": "W...",
      "requirements": {
        "b": {"source": "github:org/b", "requested": "v1.2.3"}
      }
    },
    "d": {
      "source": "https://github.com/org/d.git",
      "commit": "Z...",
      "requirements": {}
    }
  }
}
```

Install store: `.nift/packages/{a,b,c,d}` — each a real directory, remote
packages detached at their pinned commits.

Root-to-`b` explanation (from manifest + lock only): root requires `a` and
`c`; `a`'s node edges require `b` (`latest`), `c`'s node edges require `b`
(`v1.2.3`); both requirements resolve to the single `b` node at commit `Y`;
therefore `b` is present because both `a` and `c` require it, at `Y`.

Conflict variant: if `latest` resolved to `Y2 != Y`, then `a`'s edge
(`b@latest -> Y2`) and `c`'s edge (`b@v1.2.3 -> Y`) demand different commits
for the same canonical source → fatal conflict naming both paths; no lock
emitted.

Cycle variant: if `b` also required `a`, the closure walk detects the
`a -> b -> a` cycle → fatal cycle error; no lock emitted.

## Independent design review (of this companion + the Batch 5 plan)

| Check | Result |
| --- | --- |
| lost edge requirement information | prevented: per-node `requirements` records every parent's `{source, requested}`; node holds canonical `source` + `commit` |
| ambiguous package identity | prevented: one node per package name; compatibility rule explicit |
| nondeterministic floating-ref resolution | prevented: memoized canonical-requirement->commit per transaction; `install` uses the lock; only `update` re-resolves |
| CWD-dependent local paths | prevented: relative local source resolves against the declaring package manifest directory |
| false cross-machine reproducibility claim for local deps | corrected: `local` is graph-deterministic, contents intentionally live; exact-commit reproducibility only for Git |
| targeted-update ambiguity | pinned: `<name>` restricted to root deps; global shared-node compatibility; atomic conflict failure |
| v1/v2 half-migration | pinned: read-only keeps v1; first mutating op emits v2 atomically; commands do not write v2 until CP12 |
| Batch 4 recoverability accidentally broadened | prevented: acquisition/resolution failures are fatal command/rollback outcomes; only runtime import codes stay recoverable |
| inability to reconstruct dependency paths from the lock alone | prevented: root manifest + lock edges reconstruct all paths without installed-package reads (CP10 schema test) |

`docs/handover/V4.6-BATCH-5-DEPENDENCY-GRAPH-DESIGN.md` remains authoritative
for the audit, checkpoint plan, review gates, compatibility risks and test
matrix; this companion pins the exact contracts above it. No implementation.
No tag/release. The unrelated dirty `nift-packages/sqlite` repo is not
