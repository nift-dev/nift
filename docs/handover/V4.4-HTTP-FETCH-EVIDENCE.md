# Nift v4.4 HTTP/fetch evidence checkpoint

## Decision

Do **not** add a native HTTP/fetch primitive to the v4.4 core yet.

The package system plus `run()` gives packages a viable HTTP escape hatch through an installed client such as `curl`, while keeping Nift core independent of TLS/HTTP libraries. The first package (`sqlite`) does not require HTTP at all; it uses the local `sqlite3` executable. There is therefore not yet enough package evidence to justify restoring a networking dependency.

## What to measure during dogfooding

Track how many real packages/migrations need HTTP, whether they repeatedly wrap `curl`, how much structured response/header handling they duplicate, and whether requiring an external HTTP executable materially hurts portability or agent workflows.

If repeated use establishes the need, compare mature cross-platform C/C++ clients on: TLS/platform trust stores, redirects/proxies/compression, HTTP/2 support, static/dynamic size, Windows/macOS/Linux behavior, Snap packaging/confinement, maintenance activity and license. Re-evaluate libcurl rather than rejecting it solely because of the old Snap/classic-confinement concern.

Production HTTPS should not be implemented casually inside Nift itself.
