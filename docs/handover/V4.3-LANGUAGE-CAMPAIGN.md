# Nift v4.3 language campaign handover

## Scope

This is the agreed game plan for the next Nift language campaign. It is not release authorization. Database/API access is deferred. Preserve the v4 principle: useful build/template facilities are native Nift features; do not restore LuaJIT.

Target surface:

```text
++ / --
+= -= *= /= %=
64-bit numeric review
mutable arrays
stack
queue
prique
map / sorted_map
set / sorted_set
lambdas
first-class callable values
lexical closures
higher-order functions
map/filter/reduce/any/all/find/count/sort transformations
```

`map` and `set` preserve insertion order. Consider `fast_map` / `fast_set` only later if profiling demonstrates a real performance need. `prique` is the public spelling for priority queue.

## Collection contract

Arrays gain:

```nift
push(value)    pop()
insert(i,v)    remove(i)
first()        last()
indexOf(value) contains(value)
size()         empty()
clear()
```

Frozen for v4.3: `first()`, `last()` and `pop()` fail on an empty array; `indexOf()` returns `-1` when absent; `insert()` accepts indices `0..size`; `remove()` requires an existing index. `string += string` is supported. `sort()` mutates the collection and returns the collection result; custom comparators use a boolean "a before b" contract. `stack` uses `top()`. `prique ==` uses identity semantics. `same()` rejects scalar values. Initial map keys/set members are stable scalar values only (bool/int/double/string; null is excluded).

`stack` is LIFO; `queue` is FIFO. Keep their APIs conventional and small (push/pop, top/front or a frozen `peek` spelling, size/empty/clear, contains where useful). Their `for` traversal order must be documented.

`prique` is priority ordered. Do not expose heap representation or iterators. It does not need structural equality. Preferred contract: `==` uses identity semantics, like structs/callables, and `same(a,b)` explicitly tests identity. CP1 may instead choose to reject `prique ==`; do not define equality by heap representation or logical dequeue sequence.

`map` preserves insertion order for iteration. Updating an existing key should retain its position; removing then reinserting should place it at the end. Map equality compares key/value contents and ignores insertion history.

`sorted_map` iterates by key comparison but has the same logical key/value equality semantics.

`set` preserves insertion order. Set equality compares membership and ignores insertion history. `sorted_set` iterates by value comparison while equality remains membership-based.

## Equality, identity, ordering and hashing

Do not add JS-style coercive equality or `===`.

```text
null        value equality
bool        value equality
string      value equality
numbers     numeric equality, including int/float cross-comparison
array       structural equality
stack       structural sequence equality
queue       structural sequence equality
map         structural key/value equality; insertion order ignored
sorted_map  structural key/value equality
set         structural membership equality; insertion order ignored
sorted_set  structural membership equality
struct      identity equality
callable    identity equality
prique      identity equality preferred; non-comparable is acceptable if frozen at CP1
```

Examples:

```nift
1 == 1.0              // true
1 == "1"             // false
[1,2] == [1,2]       // true
```

Add explicit identity testing:

```nift
a := [1,2,3]
b := a
c := copy(a)

a == c       // true
same(a,b)    // true
same(a,c)    // false
```

Freeze `same()` on scalar/non-reference values at CP1; prefer a clear type error rather than making it an alias for `==`.

Mutable compound values must not accidentally become unsafe hash keys. Initially prefer stable scalar map keys (bool/int/float/string, optionally null). If `1 == 1.0`, hash lookup must treat them equivalently. Set member eligibility must be frozen explicitly: either restrict to safe hashable values initially or use a representation that safely supports broader structural values.

Before sorted collections, sort or default `prique` comparison, freeze total-ordering rules. At minimum numbers (including int/float cross-comparison) and strings are orderable. Do not invent arbitrary ordering for arrays, structs, collections or callables.

## No cyclic user data graphs

Do not permit cyclic user-visible data/object graphs. Mutations that would create direct or indirect cycles through mutable compound values must fail deterministically. Add adversarial tests. Structural equality/copy/deepcopy need not support arbitrary cyclic user data.

Closures necessarily retain lexical environments internally; manage those lifetimes safely without exposing arbitrary cyclic data graphs. Recursive functions remain valid control flow.

## Numeric review

Preferred integer contract: signed 64-bit (`std::int64_t` or equivalent exact-width semantics).

Floating contract: plain C++ `double` (IEEE-754 binary64 on supported targets). Do not use `long double`; the extra precision is not worth its platform variability/cost for Nift. Verify Linux/macOS/Windows behavior.

Review int/int, float/float and int/float equality/order; promotion; compound assignment; overflow/underflow; ++/-- boundaries; modulo; formatting/interpolation; JSON interaction; and real Nift performance.

## Operators

Add:

```nift
i++  i--  ++i  --i
x += y
x -= y
x *= y
x /= y
x %= y
```

These are real lvalue operations. Prefix returns the updated value; postfix returns the old value; targets are evaluated exactly once. Test locals, mutable accessible struct fields and indexed/keyed lvalues where existing assignment semantics support them. Freeze string `+=` explicitly.

## First-class callables and lambdas

Named functions and lambdas share one callable value model. They can be assigned, passed, returned, stored where ordinary values are legal, and invoked indirectly.

Lambda syntax:

```nift
x => x * 2
(a, b) => a + b
() => 42

x => {
    if(x < 0) { return -x }
    return x
}
```

A user-defined lambda is simply a lambda expression assigned to a value:

```nift
double := x => x * 2
add := (a,b) => a + b
result := double(10)
```

Avoid a redundant second `lambda(...)` declaration syntax unless parser evidence requires it.

## Closures

Closures capture lexical **bindings**, not value snapshots:

```nift
factor := 10
multiply := x => x * factor
factor = 20
multiply(2)             // 40
```

Mutable captured state and escaping closures are intended:

```nift
fn(counter(start)) {
    count := start
    return () => count++
}

next := counter(10)
next()                  // 10
next()                  // 11
```

Captured environments must safely outlive declaring frames. Freeze copy/deepcopy, `same`, callable identity, private-member access, recursion and error interactions.

## Higher-order transformations

Both named functions and lambdas work wherever a callable is accepted. Agreed family:

```text
map filter reduce any all find count sort
```

Examples:

```nift
doubled := values.map(x => x * 2)
evens := values.filter(x => x % 2 == 0)
total := values.reduce((acc,x) => acc + x, 0)
has_large := values.any(x => x > 100)
all_valid := values.all(x => x >= 0)
first_large := values.find(x => x > 100)
n := values.count(x => x > 100)
values.sort((a,b) => a < b)
```

Freeze no-match `find`, comparator semantics, sort mutation-vs-copy behavior, map callback argument shape, and result type/order. Do not force every transformation onto every collection when semantics are unnatural.

## CP2 architecture map

The current expression runtime is centered in `Parser::evaluate_expression`; bindings are `VariableBinding` objects owning shared `json::Document` storage, structs use explicit instance identities, callable frames use parser-managed scopes, and array/object literals use Jsonic documents. v4.3 extends these shared seams rather than adding a second evaluator. Array aliases intentionally share binding storage; `copy`/`deepcopy` produce distinct array storage. Existing assignable struct-member paths remain the lvalue boundary until indexed/keyed assignment itself is introduced.

Numeric storage keeps `double` for floating values. Nift integer expressions use signed-64-bit semantics; integer spellings outside binary64's exact range retain exact decimal spelling internally and integer arithmetic checks signed-64-bit overflow rather than silently rounding.

## Architecture rule

Build shared runtime concepts for ownership/identity, structural equality, `same`, comparison, hash/key eligibility, copy/deepcopy, cycle prevention, lvalues, internal iteration, callable invocation and captured lexical bindings. Do not build each collection as an unrelated special case. Iterators remain internal; users get `for` and collection operations, not iterator objects.

## CP35 / CP37–CP44 implementation update

CP35 certifies returned closures and multiple closures sharing one captured binding (including callable values stored through mutable arrays). CP37–CP44 add higher-order methods to arrays and applicable native collections. `map`/`filter` return arrays; `reduce` requires an explicit initial accumulator; `any`/`all` short-circuit; `find` returns `null` when no value matches; `count` returns the number of matches. Map callbacks receive `(key, value)`. Array `sort()` mutates in place, is stable, uses natural numeric/string ascending order by default, and accepts a boolean less-than comparator such as `(a,b) => a > b` for descending order. Inline lambdas inside method calls are parsed as nested expressions rather than being mistaken for a top-level lambda. Focused evidence is `tests/v43_cp35_cp44_smoke.sh`.

The development version is now `4.3.0` in the executable and Snap metadata. No tag, push, release, package publication, or website deployment is authorized by this workspace.

### Findings reported, not fixed (contract/design gaps)

- **Struct self-reference cycles are not rejected.** `@struct(node){next :=
  other()}` followed by `a.next = a` creates a cycle; the frozen contract says
  cyclic-mutation attempts must fail deterministically. It does not crash
  (structural equality on structs is identity; `deepcopy`'s seen-map handles
  it), but the invariant is not enforced.
- **Collection methods cannot be invoked through struct-field member paths**
  (`obj.c.size()` / `obj.c.set(...)` fail for a struct field holding a
  collection). Member-path method dispatch for collection/array methods is not
  implemented.
- **`@for` over a map requires string keys**; maps with numeric keys cannot be
  iterated, even though numeric keys are supported by the map API.
- **Mixed int64/double ordering beyond the exact int64 range errors**
  (`9223372036854775807 < 1e19` fails rather than returning true).
- **Array/collection methods require a binding root**; inline literals such as
  `[3,1,2].sort()` are not supported.
- **Array literals cannot contain struct/callable/collection references**
  (literal parsing is JSON); `push` of a reference value works.
- `contract/filesystem_recovery_smoke.sh` showed a timing flake in this
  environment (passed on re-run); not a v4.3 production change.

CP36 (closure ownership/leak/sanitizer certification) and CP45-CP50 remain not
started.

## Pre-certification contract closure (review-correction record)

Before CP36/CP45-CP50, the two frozen-contract violations found by the
independent review were resolved, plus one additional CONTRACT_VIOLATION.

- **Forbidden user-visible cycles now fail deterministically.** `Parser::reference_would_cycle`
  walks struct fields and collection values (struct/collection references are
  graph edges; callables are leaves because their captured lexical environments
  are internal; array values are plain copies) and rejects any mutation that
  would create a direct or indirect cycle: struct field assignment (member and
  receiver paths), collection `push`, and map `set` value. Self-references,
  indirect struct cycles, longer cycles, and collection->struct->collection
  cycles are rejected; acyclic sharing, aliases, copy/deepcopy and callables in
  collections remain legal. Covered by `tests/v43_review_smoke.sh` and
  `contract/v43_language_smoke.sh`.
- **Mixed int64/double comparison is complete across the full range.** A unified
  `numeric_compare` compares exact int64 operands without lossy conversion; a
  double is handled by magnitude so `9223372036854775807 < 1e19` is `true`,
  `9223372036854775807 < 9223372036854775808.0` is `true`, `INT64_MIN` and
  negative-large-double cases work, and equality/ordering always agree
  (e.g. `9007199254740992 == 9007199254740992.0` with `<`/`>` both false).
  CP5/CP20/CP25 are now genuinely satisfied and remain numbered as before.
- **Map `@for` iterates typed entries directly (no JSON-object
  materialization).** `@for((key, value) : map)` binds the original typed key
  and value from the map's ordered entry sequence, preserving the key domain
  and ordering (insertion for `map`, sorted for `sorted_map`) without
  stringification or a temporary object representation. `1` and `"1"` (and
  `true` and `"true"`) are distinct iterated keys, `m.get(key)` round-trips the
  typed key during iteration, and `1`/`1.0` remain one logical numeric key.
  This closes the CONTRACT_VIOLATION where maps with numeric keys could not be
  iterated and supersedes the earlier stringifying materialization.

Classification of the other reported limitations:

| Limitation | Classification | Action |
|---|---|---|
| Collection methods via struct-field member paths (`obj.c.size()`) | UNSPECIFIED | Not promised nor excluded by the frozen grammar (member-path method dispatch is not implemented). Documented; do not extend in v4.3. |
| Binding-root method requirement (`[3,1,2].sort()`) | INTENTIONAL_BOUNDARY | Methods require a binding root; inline literals are not method receivers. Documented; do not broaden. |
| Reference values in array literals (`[() => 7]`) | INTENTIONAL_BOUNDARY | Literal grammar is JSON; reference values are stored via `push`/assignment. Documented; do not change the literal grammar. |

Keep the existing **Core reference** focused on what is useful when building
websites with Nift: template directives, `$[...]`, metadata, paths/tracked
files, JSON/schema, loops, functions/fragments, structs, expressions and the
collection/value features that are useful in templates.

The conceptual split is:

```text
template land

script land
```

### Independent review / correction record (native scripting)

A review/correction pass independently verified the scripting implementation
against the frozen contract (architectural reuse, `@script`, `@import`/
`export`, array/string ergonomics, string composition, filesystem, streams,
console I/O, `nift run`, `nift sh`) and corrected the following defects:

1. **Quoted string literal leniency** (`scalar_literal`). A value whose first
   and last characters were both quotes was accepted as one string token, so a
   string concatenation such as `"a" + "b"` was mis-parsed as the single
   string `a" + "b` before the concat step ran. `scalar_literal` now requires
   the first unescaped closing quote to be the final character.
2. **String `+` associativity and double evaluation.** The concat scan used the
   leftmost top-level `+`, producing right-associative results (`1 + 2 + "x"`
   was `12x` instead of `3x`), and numeric `+` operands were evaluated twice
   because the scan fell through to the generic binary handler (a mutating
   operand such as `(x := 5) + 1` double-declared). The scan now finds the
   rightmost top-level `+` (left-associative) and resolves numeric `+` itself
   so operands are evaluated exactly once.
3. **Silent swallowing of unresolvable script statements.** The template
   lenient-literal fallback also swallowed statements that fail to evaluate in
   script hosts, so `nift run`/`nift sh`/`@script`/`@import` could exit zero or
   render nothing on garbage. Script hosts now run in strict mode: an
   expression that does not resolve is a reported error. Ordinary template
   rendering keeps its pre-existing lenient literal behaviour.
4. **`read_val` diagnostics.** The parse error was discarded and replaced with
   an empty `read_val: ` message; the real parser error is now surfaced.
5. **`export()` under `nift run`/`nift sh`.** Exporting outside an import
   previously errored, which broke the "same file importable and runnable"
   design (CP83). It now validates the named binding and records it with no
   importer/consumer; unknown bindings still error, and `@import` validation
   (missing/duplicate/collision, return-value rejection, cycles) is unchanged.
6. **`print()`/`write()` quoted-literal interpolation.** A directly-quoted
   literal argument such as `print("hello, $[name]")` bypassed expression
   evaluation and was emitted verbatim. Quoted literals are now interpolated
   once before rendering (CP70/CP79); evaluated (non-literal) values are never
   re-interpolated.

### Final presentation model

Presentation modifiers compose over the original value, never over each
other's string output:

```text
original Nift value
        |
        +-- formatting        (.stringify() compact / .prettify() pretty)
        |
        +-- presentation      (plain / .highlight() REPL-only syntax colour)
```

`x.prettify().highlight()` and `x.highlight().prettify()` therefore both mean
"pretty + highlighted" of the original value. Repeated modifiers are
idempotent (`x.prettify().prettify() == x.prettify()`). `highlight()` does not
change formatting (it leaves the compact form unless `prettify()` is also
present) and never embeds ANSI in a returned string; colour is applied only
when the REPL inspects the value on a colour-capable terminal. `nift run`,
`@script`, templates and file/stream output are never ANSI-contaminated.

The presentation matcher only recognises a genuine top-level presentation
chain. A compound expression such as `x.prettify() == x.prettify()` or
`"x" + x.prettify()` is evaluated by the ordinary machinery, and a string
literal such as `"a.prettify()"` is not mistaken for a presentation call.
Method-call dispatch (collection/array/stream/callable/struct) claims a call
only when its closing paren is the final character, so `x.size() == x.size()`,
`f(1) == f(1)` and struct-method operands evaluate correctly. `resolve_direct`
defers a struct member that is a method to the call machinery while genuine
missing-field errors are preserved.

### Final REPL prompt contract

```text
~/path$
```

Presentation: the pwd/path is **bold green**; a path beneath the resolved home
directory abbreviates the home prefix to `~` (the exact home directory shows
`~$`, not `~/` or `/home/<user>$`); `$` uses the normal/default terminal
styling. Home abbreviation is path-aware (a `/home/<user>2` sibling is never
abbreviated) and uses the real `HOME`/resolved home, not a hard-coded
`/home/<user>` assumption, so macOS/Windows behave correctly.

### REPL bare-expression display

A single bare expression in `nift sh` displays its safe value (compact by
default; the pretty form when `.prettify()` is in the chain; syntax-coloured
compact/pretty when `.highlight()` is present and the terminal supports colour).

Suppression rule:

```text
result == null   -> no REPL output
result == ""     -> no REPL output
0 / false / [] / {} / empty collections -> still displayed
```

This keeps null-returning commands such as `cd(path)` silent without hiding
falsy/empty values.

`cat(path)` writes the file bytes exactly to the console sink with no implicit
trailing newline and returns `null`; missing files and directories are errors.
`ls()` / `ls(path)` return a deterministically filename-sorted array of entry

## CP85 implementation record — parser-reported multiline REPL input

The REPL no longer uses a brace-balancing heuristic. `Parser::statement_state()`
returns one of:

```text
Complete    balanced and translatable into a valid statement program
Incomplete  the submitted text is an unterminated prefix (unclosed quote,
            parenthesis, bracket or brace)
Invalid     balanced but malformed
```

The REPL loop asks the parser for the state of the accumulated input: an
`Incomplete` prefix keeps reading with the continuation prompt, a `Complete`
statement is executed, and an `Invalid` form is executed so the canonical
diagnostic is shown and the session survives. `statement_state` uses the same
quote-aware delimiter conventions as the function-program translator (no
separate comment grammar in statement land); unmatched closing delimiters are
`Invalid`, not merely incomplete. EOF terminates an incomplete session cleanly.

The review also corrected a pre-existing statement-scanner defect that CP85
exposed: the function-program `convert` statement delimiter scanner tracked
only parentheses and brackets, so a multiline block lambda (or any statement
containing a `{...}` block) was split at a newline inside the braces. The
scanner is now brace-aware, so multiline block lambdas such as:

```nift
f := (a) => {
  return a * 2
}
```

work under both `nift run` and `nift sh` (previously the newline inside the
block split the statement and the body was mis-parsed). Multiline functions,
structs, lambdas, conditionals and nested loops, braces inside strings,
escaped quotes, malformed-incomplete input, recovery and EOF termination are
covered by `tests/v43_cp85_repl_multiline_smoke.sh`, wired into
`test-v43-language` / `make test`.

- [x] **CP105 — freeze the managed FileValue contract.** `file(path)` constructs a path-backed identity/resource value without opening the file or performing content I/O. ### Frozen managed-file lifecycle

```text
file(path)
    CLOSED
       |
       | open(mode)
       v
    OPEN CLEAN
       |
       | content mutation
       v
    OPEN DIRTY
       |          |
       | save()   | revert()
       v          v
    OPEN CLEAN  OPEN CLEAN
       |

       v

close() while DIRTY

host/session termination while OPEN DIRTY
    -> ERROR + discard unsaved working state + physical cleanup
    -> filesystem remains at last successful save
```

# CP115-CP167 — structured data, agent eval, project model and typed-content campaign

This campaign follows the accepted CP114 baseline and deliberately keeps CP48-CP50 held. It extends the same v4.3 value/expression/runtime rather than introducing a second query language, a jq embedding, a CMS-specific evaluator, or a second schema system.

## Frozen direction before implementation

- Value operations use method syntax consistently (`obj.keys()`, `text.to_double()`, etc.).
- JSON/object/collection operations must have identical semantics in templates/scripts and the agent-facing CLI evaluator.
- Expose one standalone expression host (`nift eval`) backed by the existing expression engine; do not fork expression semantics.
- Expose a read-only semantic `project` object both at build/template time and through `nift eval` when a project context exists.
- Content metadata uses conventional YAML front matter (`---` delimiters).
- A tracked file may instead name one external front-matter file in `.nift/tracked.json`; inline + external front matter is a hard error. Do not merge multiple front-matter sources.
- `.nift/tracked.json` may assign a content `type` to a file entry. If front matter also supplies `type`, require agreement; disagreement is an error.
- Schema definition sources use the `.schema` extension; taxonomy definition sources use `.tax`. Do not use `.nift` as the extension for either.
- `.nift/config.json` may explicitly list schema and taxonomy definition files. Prefer explicit configuration over magic directory scanning.
- Keep taxonomies first-class and use familiar taxonomy terminology. Taxonomy terms normally emerge from content; explicit term/configuration metadata can be layered on where needed.
- Typed-content discovery belongs under the project model. The provisional public shape is `project.content.post`, dynamic `project.content[type]`, `project.schemas.post`, and `project.taxonomies.tag`; dogfood before final freeze.
- Schemas/taxonomies are project/template definitions; content files normally only select a type and supply metadata/content.
- All new project/content/taxonomy query surfaces use the ordinary Nift value and collection machinery.
- Preserve Nift's deterministic/local-input model, path confinement, incremental correctness, standalone-binary goals and performance character.

## Typed-content build performance investigation and correction

The CP115-CP167 review measured superlinear full-build scaling (100/250/500/
1000/2000 pages in 0.01/0.07/0.28/1.15/4.86s; a 10,000-page ordinary build
took ~95s against the ~0.11s certified baseline) while the CP165-certified
`nift eval` query path remained linear.

Reproduction and historical comparison: a controlled matrix (100-10,000 pages,
3 repetitions, min-wall) reproduced the curve. A no-change incremental rebuild
was fast (model cached per build), ruling out per-build reconstruction. The
curve persisted with `.html` content (no markup conversion), without schema/
taxonomy config, without `project.*` template references, and with an empty
template, isolating it to the base project build path rather than any typed-
content feature.

Root cause (profiling evidence): `ProjectInfoHost` constructed
`make_project_value()` in its constructor, and `ProjectInfoHost` is created
once per tracked page inside `ProjectInfo::build_one` (ProjectInfo.cpp).
`make_project_value()` reads every content file, parses every front matter,
validates schemas and builds taxonomy reverse indexes, so a build of n pages
rebuilt the entire project model n times: O(n^2).

Correction (production): `ProjectInfo` now memoizes the immutable project
model lazily with `std::call_once` (thread-safe under the parallel build);
`ProjectInfoHost::binding("project")` resolves it only when a page actually
references `project`. Plain builds no longer construct the model at all, and
project-using builds construct it exactly once and share it across pages.

After scaling (min-wall, 3 reps, this machine):

```text
pages      before      after
100        0.01s       0.01s
250        0.07s       0.01s
500        0.28s       0.02s
1,000      1.15s       0.04s
2,000      4.86s       0.07s
5,000      -           0.19s
10,000     95.57s      0.44s
```

The curve is now approximately linear (10x pages -> ~10x time). At this point a
further superlinear cost remained for templates that reference `project.*`: a
project-using page recorded every tracked file path as a dependency (the
Parser.cpp project-root dependency loop), so n project-using pages did O(n^2)
dependency bookkeeping. That behaviour was treated here as a documented
correctness-first tradeoff; it has since been eliminated in the separate
"semantic project dependency" investigation below, which replaced per-file
dependency expansion with a compact project fingerprint.

Memory/RSS: the shared model is constructed once and shared via
shared_ptr<const Document>; no per-page deep copies. RSS for the 10,000-page
build stayed well within normal bounds.

Incremental correctness: unchanged and re-verified (content edits, adds,
removals, retyping, and schema/taxonomy config changes still propagate to
dependent pages; clean-vs-incremental output equivalence holds; template/eval
parity holds).

Regression/performance coverage: `benchmarks/typed_content_scaling.py` builds
250 and 1000 typed-content pages and fails if the time ratio exceeds 8x for
4x pages (near-linear ~4x; the historical quadratic path ~16x), wired into
`test-v43-language`. This closes the CP165 blind spot that measured only the
eval query path.

## Second investigation: semantic project dependency (coarse project.* scaling)

A separate, later performance/correctness campaign. The first investigation
fixed per-page project-model reconstruction. This one fixes the remaining
behaviour: a page referencing `project.*` registered every tracked file path as
a dependency, so n project-using pages did O(n^2) dependency bookkeeping (both
in page-info size and in incremental staleness evaluation).

### Old dependency architecture

```text
page references project.*
    -> Parser project-root dependency loop
        -> .nift/config.json
        -> .nift/tracked.json
        -> every tracked content file path
        -> every schema/taxonomy source path

n project-using pages x n tracked files
    -> O(n^2) dependency records in page-infos
    -> O(n^2) staleness checks on the next build
```

Additionally, two O(n^2)-shaped build costs surfaced during profiling even
after the fingerprint dependency replaced the per-file list:

```text
Parser constructor (once per page render)
    -> scanned the whole project.files array to find this page's own metadata
    -> O(n) per page -> O(n^2)

final_postfix method dispatch on a project array/object receiver
    -> eval(receiver) deep-copied the whole collection into a json::Document
    -> O(n) per page -> O(n^2)
```

### Reproduction/scaling evidence (before)

With every page using `project.files.size()`, the project-using full build
scaled superlinearly (all timings min-wall on this machine):

```text
pages        before(full build)      pages        before(full build)
100          0.01s                   2,000        3.89s
250          0.02s                   5,000        4.86s
500          0.30s
1,000        1.09s
```

10,000 project-using pages took ~30s+ (extrapolated) before the fix; the
ordinary full build was 0.44s. Incremental staleness evaluation also carried an
O(n) dependency check per project page.

### Root causes

1. Per-page scan for own metadata: the Parser constructor resolved
   `project.files` and linearly searched it for `tracked_info_.name`.
2. Per-page receiver deep copy: `final_postfix` evaluated the receiver
   (`project.files` etc.) via `eval(receiver, base)`, which deep-copied the
   whole collection before dispatching `size()`/`empty()`/`keys()` etc.
3. Per-file dependency expansion: the Parser project-root dependency loop
   inserted every tracked file path (and schema/taxonomy source) into the
   page's dependency set.

### Design selected

A compact semantic project dependency backed by a deterministic model
fingerprint:

```text
project model (immutable, built at most once per build)
    -> project_fingerprint_of(model)   = FNV-1a 64 over the canonical dump
    -> .nift/project.fingerprint file  = written only when the fingerprint CHANGES

page referencing project.*
    -> dependencies: config.json, tracked.json, .nift/project.fingerprint
    -> page-info additionally records the fingerprint VALUE it was built against
       ("project-fingerprint" field)

next build staleness check for the fingerprint dependency
    -> refresh (rebuild shared model once per build if not already cached)
    -> compare CURRENT fingerprint value vs the page-info's stored value
    -> differ   -> rebuild (project model changed)
    -> equal    -> clean
```

The value comparison (not the fingerprint file mtime) decides staleness,
because within one fast build the fingerprint write and the page-info write can
share a filesystem timestamp, which made an mtime comparison falsely report a
change on the immediately following build.

Addition/removal/rename/retype/schema/taxonomy changes all change the model and
therefore the fingerprint, so a page depending on `project.content.post`
rebuilds when a brand-new post appears even though that file was never in its
old physical dependency list.

### Production changes

- `ProjectInfo`: `project_fingerprint_of()` (deterministic FNV-1a 64 over the
  model's canonical serialization), `write_project_fingerprint()` (write only
  when the value changed, preserving mtime on no-change), `refresh_project_fingerprint()`
  (ensure the shared model and fingerprint reflect current state), and
  `tracked_index_of()` (O(1) name -> tracked index). `project_value()` now
  writes the fingerprint inside its `std::call_once`.
- `Parser` project-root resolution: replaced the per-file dependency loop with
  the three O(1) entries (config, tracked, fingerprint).
- `RenderHost`/`ProjectInfoHost`: new `project_file_value(name)` virtual that
  resolves a page's own file entry in O(1) through the tracked index, removing
  the per-page scan of `project.files` in the Parser constructor.
- `Parser::final_postfix`: a copy-free fast path for read-only container
  methods (`size`/`length`/`empty`/`first`/`last`/`keys`/`values`/`entries`)
  that resolves a pure JSON-path receiver through the aliasing JSON walker
  instead of `eval(receiver, base)` (which deep-copied the whole collection).
  Falls back to the normal evaluator for non-path receivers (structs,
  collections, streams, file values, function results).
- `ProjectInfo::build_reasons`: the `.nift/project.fingerprint` dependency is
  decided by value comparison against the page-info's stored fingerprint, not
  by file mtime/hash.

### Correctness invariants

- Any `project` access (direct member, loop, function argument, computed path)
  resolves the root through `resolve_json_value`, which registers the compact
  project dependency, so dynamic access falls back to the broad semantic
  dependency (never an unsafe narrow one).
- The fingerprint is deterministic: same inputs -> same hash, so no-change
  builds do not rewrite it and pages stay clean.
- No page-info mtime/fingerprint mtime ordering assumption is made; staleness
  is a value comparison.
- Correct invalidation remains mandatory and coarse: a project change rebuilds
  every project-using page. Correct output is still preferred over fast stale
  builds.

## Third investigation: v4.2.0 parity / pay-for-what-you-use

A read-only benchmark against released Nift v4.2.0 exposed unnecessary eager
work on the ordinary build path; the follow-up production correction removed
it. This section is a clearly separated record so future comparisons do not
mistake feature differences for implementation regressions.

### Released baseline

```text
v4.2.0   annotated tag v4.2.0 -> commit 577b74d22adf4ae2da0de70638f5d142d8b3e76d
         (smaller feature surface; NO project model / typed content / schemas /
          taxonomies / structs / functions / agent features)
v4.3     current dev HEAD (150fa92 before this pass; 52ca921 after)
```

Both built with identical flags (g++ -std=c++17 -O2) on identical fixtures.

### Initial benchmark (read-only)

Ordinary full build (median wall, output byte parity YES):

```text
pages      v4.2.0      v4.3-before    ratio
100        0.005s      0.007s         1.48x
1,000      0.021s      0.034s         1.61x
5,000      0.059s      0.144s         1.85x
10,000     0.126s      0.291s         1.69x   (RSS 10.7MB -> 58.0MB)
```

Incremental (10k, median): no-change 1.05x, body edit 2.24x, front matter
2.07x, template edit 1.75x, add 2.27x, remove 1.03x. No-change/remove were
near-parity; content/model-affecting operations were ~2x.

### Eager-work findings (root cause)

1. The v4.3 Parser constructor called binding("project") unconditionally,
   building the full project model (reading every content file, parsing front
   matter, building schemas/taxonomies/reverse indexes) on EVERY build even
   when no template referenced project.*. Evidence: an ordinary v4.3 build
   created .nift/project.fingerprint; v4.2.0 never does.
2. ScriptRenderHost (nift eval / nift run) built make_project_value in its
   constructor whenever it found a project root, so an ordinary `nift eval`
   in a project directory paid for the model.
3. The rest of the v4.3 runtime (functions/fragments, structs, richer
   expressions, JSON machinery, per-page front-matter state) was classified
   CHEAP BASELINE / LAZY and did not scale with project size.

### Pay-for-what-you-use corrections (production)

- Parser ctor: per-page metadata via RenderHost::page_project_metadata() using
  a shared compute_tracked_metadata() (front matter + type + schema
  validation), without building the project-wide model. The frontmatter
  binding is byte-identical to the model path because both use the same helper.
- Project-wide model: lazy, built at most once per build on first project.*
  access (or fingerprint refresh for project-aware pages).
- ScriptRenderHost: loads cheap config/tracked eagerly; builds the model lazily
  on first project.* access.
- ProjectInfo caches content_model (schemas/taxonomies) once; mandatory
  validation (schema/taxonomy file load, per-page schema/type-conflict errors)
  stays eager; optional query/index construction (project.files/content/
  taxonomies, reverse indexes, taxonomy slug validation, the project
  fingerprint) is deferred to the lazy model.
- Removed the now-unused project_file_value()/tracked_index_of() seams.

### Deliberate error-semantics decision

Mandatory validation remains eager and fails identically (malformed schema
file, unknown content type, bad front matter, per-page schema/type errors all
verified byte-identical before/after). Taxonomy reverse-index slug validation
is part of optional query/index construction and is deferred to the lazy
model: it surfaces when project.* is accessed (identically to before); a
project that configures taxonomies but never accesses project.* no longer
overrides every page's frontmatter._error with the unused index's slug error.
This is the "separate mandatory validation from optional query/index
construction" boundary, not a lost validation.
