# Nift v4.4 AST / execution-engine performance campaign

## Purpose

Nift v4.4 has grown into a real scripting language and shell as well as a website generator. The current evaluator is still substantially string-driven: expressions and statement fragments are repeatedly scanned, classified, split and evaluated from source text. Profiling during the v4.4 scripting benchmark campaign found that this machinery is now a major common runtime cost across loops, arithmetic, collections and BFS.

This campaign tests a deliberate next architecture: **parse expressions and statements once into an AST, then execute the tree against the existing dynamic Nift runtime**. It is an evidence-driven migration, not permission for an unconditional rewrite. The existing evaluator remains the compatibility oracle until the AST path proves both semantic parity and worthwhile performance.

A second, independent track attacks JSON overhead. Nift embeds JSONIC++, whose native parser is already highly competitive; Nift should not discard that advantage through unnecessary copies, conversion, binding or interpreter overhead. JSON parsing, traversal, mutation and serialization must be decomposed and optimized independently of the AST work.

## Current evidence and motivation

The v4.4 benchmark campaign has already found several general runtime pathologies rather than benchmark-specific problems:

- array `push()` repeatedly deep-copied its receiver, producing accidental O(n^2) construction;
- set membership/addition used repeated linear scans; a scalar-key index restored near-linear construction and moved the large map/set workload from roughly 82 seconds to roughly 2 seconds;
- map scalar-key operations had the same class of indexing problem and were repaired;
- compound assignment and increment/decrement unnecessarily round-tripped plain identifiers through generated expression strings; direct assignment materially improved arithmetic/loop-heavy workloads;
- Callgrind subsequently showed a broad remaining signature dominated by string/expression machinery (`std::string` work, scans such as `rfind`, literal/type classification and recursive expression evaluation);
- fair pre-generated JSON parsing showed that the previous multi-second JSON-parse aggregate was mostly interpreted input construction, but Nift's remaining `inject()` overhead still needs to be accounted for and reduced.

The campaign must preserve these wins and their performance guards.

## Non-negotiable rules

1. **Measure first.** No optimization is accepted without a before measurement and profiler/scaling evidence.
2. **Preserve semantics.** Existing implementation, tests, docs and the independent regression suite define the current contract.
3. **Parse structure, not values.** AST nodes may cache syntax and resolution metadata, but mutable binding values are resolved at execution time unless a later proven-safe slot/cell model is introduced.
4. **Keep the old evaluator during migration.** It is the differential oracle and fallback until coverage and evidence justify retirement.
5. **No benchmark cheating.**
6. **JSON is its own investigation.** Do not attribute a slow single `inject()` to loop/expression overhead without evidence.
7. **Architecture must earn its complexity.** If the AST prototype produces only marginal gains, stop/revert rather than forcing a rewrite.
8. **One coherent commit per checkpoint.**
9. **Every accepted runtime change must keep all applicable tests/regressions/integrity checks green.**
10. **DeepSeek review is mandatory before broad migration/release.**

## Target architecture

```text
Nift source
    |
    v
lexer / parser
    |
    v
AST
  |- expression nodes
  `- statement nodes
    |
    v
tree-walking evaluator
    |
    v
existing bindings / json::Document values / native operations
```

Possible future evolution, only if later profiling justifies it:

```text
source -> AST -> compact IR/bytecode -> VM
```

Bytecode/JIT/LLVM are **not** part of this campaign.

# Step-by-step checkpoint checklist

**Implementation status (2026-09-20): CP1-CP16 implemented.** CP16 now prepares supported `while` conditions once as expression trees and prepares simple assignment/compound-assignment/increment bodies once as statement/expression trees, with unsupported syntax falling back to the legacy evaluator. A focused 100k-iteration `total += i; i++` script completed locally in about 0.03s on the campaign build; this is intentionally *not* recorded as an accepted speedup until CP17/DeepSeek compares it against the frozen baseline on the same machine and checks profiler evidence.


## Phase A — freeze evidence and design the experiment

### CP1 — repository and certification baseline
- Record Nift, regression-suite and scripting-benchmark HEADs and cleanliness.
- Record current local tests, independent regressions, integrity/performance guards and cross-platform certification.

### CP2 — benchmark baseline freeze
- Capture trustworthy medians for loops, arithmetic, function calls, Fibonacci, BFS, sliding-window, sort/search, frequency-count, strings, JSON parse/traverse/mutate and map/set.
- Preserve raw result identities so semantically different historical samples cannot pollute comparisons.

### CP3 — profiler baseline freeze
- Re-run Callgrind/perf on loops/arithmetic, BFS and a JSON traversal/mutation workload.
- Record string construction/copying, scans, expression classification, binding lookup and `evaluate_expression` costs.

### CP4 — AST semantic inventory
- Inventory every v4.4 expression and statement form from source/tests/docs.
- Map each construct to current parser/evaluator entry points and planned AST nodes.
- Identify dynamic/generated-expression cases needing legacy fallback.

### CP5 — AST design contract
- Define node ownership/lifetime, source spans, errors, control-flow propagation, binding resolution and legacy fallback.
- Explicitly exclude bytecode/JIT and semantic redesign.

## Phase B — expression-tree prototype

### CP6 — AST core and source spans
- Add minimal AST infrastructure and source-location support without changing runtime behavior.
- Add ownership/unit tests.

### CP7 — literal and binding expressions
- Parse/evaluate literals and binding references as nodes.
- Differential-test against the legacy evaluator; bindings resolve current values at execution time.

### CP8 — unary and binary arithmetic
- Add arithmetic/unary nodes with current precedence/associativity semantics.
- Differential-test generated expression corpora.

### CP9 — comparisons and logical expressions
- Add equality/ordering/logical nodes and exact short-circuit semantics.
- Preserve structural/reference equality behavior.

### CP10 — index/member/range/core expression forms
- Add indexing, member/dynamic access and ranges needed by representative loops.
- Preserve safe/optional access semantics where migrated.

### CP11 — call expressions
- Add native/call expression support needed for the prototype.
- Preserve argument evaluation order, errors and callable identity.

## Phase C — statement tree and hot-loop execution

### CP12 — blocks, declarations and expression statements
- Add block/declaration/expression statement nodes.
- Preserve `:=` versus `=`, scope and stable type semantics.

### CP13 — assignment and compound assignment
- Add assignment and compound-assignment nodes, including nested indexed/member assignment.
- Never regenerate source text merely to perform ordinary AST assignment.

### CP14 — increment/decrement
- Add pre/post increment/decrement nodes with exact return-value and mutation semantics.

### CP15 — `if` and control-flow result model
- Add `if`/else plus the internal result model later used by break/continue/return.
- Preserve lazy branch evaluation.

### CP16 — `while` execution
- Parse condition/body once and repeatedly execute their trees.
- Benchmark controlled hot loops against the legacy evaluator.

### CP17 — AST prototype go/no-go gate
- Re-run loops/arithmetic and Callgrind/perf.
- Require a material reduction in string/expression-processing cost and worthwhile runtime gain.
- If marginal, stop broad migration and investigate the real bottleneck; if successful, freeze evidence and continue.

## Phase D — broaden script-land AST coverage

### CP18 — `for`, ranges and iteration
- Migrate `for` and range/collection iteration.
- Rebenchmark scan/two-pointer/sliding-window workloads.

### CP19 — break and continue
- Implement structured propagation through nested AST blocks/loops.

### CP20 — user functions and return
- Represent function bodies as statement trees and implement return propagation.
- Preserve parameters, recursion and scope; benchmark call overhead.

### CP21 — lambdas, closures and first-class callables
- Preserve the settled rule that closures bind variables/cells, not snapshots of values.
- Hammer shadowing, rebinding and callable identity.

### CP22 — variadics, destructuring and argument forms
- Migrate spread/variadic and destructuring forms.
- Preserve evaluation order and hard-won cross-platform behavior.

### CP23 — arrays/maps/sets and collection expressions
- Migrate collection literals/operations.
- Preserve scalar indexes, equality semantics and the fixed linear scaling.

### CP24 — structs, enums and methods
- Preserve stable fields, `this`, reference semantics, copy/deepcopy and field restrictions.

### CP25 — null coalescing, optional/safe access and remaining operators
- Complete remaining general expression syntax with differential precedence/short-circuit tests.

### CP26 — imports, exports and script boundaries
- Integrate AST execution with `@script`, `.f`, `@import` isolation and export-to-parent semantics.
- Preserve source locations across imported files.

## Phase E — template-land integration

### CP27 — template AST/plan design
- Combine literal output chunks with expression/script/control nodes.
- Keep literal markup/text cheap.

### CP28 — `$[...]` and template expression integration
- Parse reusable template expressions once where semantics permit.
- Preserve interpolation, metadata and escaping.

### CP29 — template control fragments
- Integrate `@if`, `@for`, functions/fragments and relevant control flow with prepared nodes/plans.
- Preserve dependency discovery and output semantics.

### CP30 — full website/build dogfood
- Build Nift's website and representative projects.
- Compare outputs/contracts and measure build time plus peak memory against baseline.

## Phase F — JSON performance raid

### CP31 — raw JSONIC++ baseline
- Parse the exact benchmark fixture directly with embedded JSONIC++ in an equivalent optimized C++ build.
- Measure IO and parse separately.

### CP32 — `inject()` cost accounting
- Profile the exact Nift `inject()` path.
- Account for IO, JSONIC++ parse, document/value movement/copying, binding installation and bookkeeping.

### CP33 — eliminate avoidable JSON parse/bridge overhead
- Remove proven unnecessary copies/conversions/allocations.
- Prefer move/ownership transfer or direct representation use where safe.
- Re-run parse benchmarks and sanitizers.

### CP34 — JSON traversal profiling
- Profile array/object iteration, indexing/member lookup and binding work.
- Separate AST/interpreter overhead from JSON representation overhead.

### CP35 — JSON mutation profiling
- Profile object/array mutation and arithmetic/update patterns.
- Hunt document copies, repeated key scans, rebinding copies and conversions.

### CP36 — JSON query/transform/serialization
- Profile and optimize these paths independently on identical inputs.
- Produce a JSON-specific cross-language table; the goal is for Nift to be genuinely excellent at JSON.

## Phase G — performance breadth and runtime cleanup

### CP37 — re-profile worst remaining benchmarks
- Generate a fresh leaderboard after AST + JSON work.
- Individually profile remaining outliers such as BFS, sliding-window, sort/search, frequency-count, strings and function calls.

### CP38 — string concatenation investigation
- Revisit known `string +=` scaling.
- Measure allocations/bytes copied and prototype a safer growth strategy only if evidence supports it.

### CP39 — binding/scope resolution optimization
- If name lookup becomes dominant after AST migration, prototype resolved local slots/environment cells while preserving shadowing, closures and rebinding.

### CP40 — AST optimization pass
- Consider safe constant folding and other parse-time simplifications.
- Do not fold observable errors/side effects/runtime bindings.

### CP41 — bytecode/VM decision checkpoint
- Decide from post-AST profiles whether tree walking is sufficient.
- If dispatch/tree traversal is the new bottleneck, write a separate future bytecode proposal; do not implement it without explicit approval.

## Phase H — correctness, compatibility and release integration

### CP42 — differential corpus expansion
- Build a large legacy-vs-AST corpus covering valid results and invalid/error cases.
- Preserve reproducers for every mismatch.

### CP43 — fuzz/property testing
- Add bounded parser/evaluator equivalence fuzz/property tests, emphasizing precedence, nesting, mutation, scopes and short-circuiting.

### CP44 — sanitizer and memory certification
- Run ASan, UBSan, LSan and Valgrind/memcheck where available over AST/JSON-heavy workloads.

### CP45 — full Nift local certification
- Run all local tests, performance guards, integrity guards, package contracts and dogfood.
- Do not weaken tests/skips for AST regressions.

### CP46 — independent regression-suite certification
- Run the complete external suite; every mismatch must be understood.

### CP47 — cross-platform certification
- Run Linux, Windows and macOS matrices, with special attention to v4.4 execution/shell/variadic/path behavior.

### CP48 — benchmark full-corpus rerun
- Rebuild the optimized binary and rerun the scripting benchmark corpus.
- Regenerate aggregates and website data without mixing incompatible historical samples.

### CP49 — final performance report
- Publish internal before/after evidence for every accepted optimization:
  `workload | original | pre-AST | post-AST/JSON | speedup | Python | Ruby | Lua 5.4 | LuaJIT | Node | Bash where applicable`.
- Include startup, wall time, scaling and trustworthy RSS.

### CP50 — docs and handover reconciliation
- Update architecture/development/testing/performance handovers and website-facing implementation notes.
- Document AST architecture only after it is the actual implementation.

### CP51 — legacy evaluator retirement decision
- Decide whether the legacy string-driven path can be removed, retained only for dynamic/fallback cases, or must remain longer.
- Removal requires full AST semantic coverage and differential evidence.

### CP52 — DeepSeek adversarial review handoff
- DeepSeek independently reviews architecture and implementation, attempts to break semantics, runs broad dogfood/fuzz/sanitizers/cross-platform certification, reproduces performance claims and fixes justified defects.
- DeepSeek must not trust the implementing agent's measurements or assumptions.

### CP53 — final campaign review / v4.4 release gate
- Reconcile DeepSeek findings.
- Require clean repos, green certification, no unexplained semantic mismatch, trustworthy benchmark data and an explicit performance summary.
- Decide whether the AST work belongs in v4.4.0 or should be held for the next release based on risk and evidence.
- **STOP for maintainer review. Do not tag or release automatically.**

## Go/no-go performance criteria

The most important early gate is CP17. The exact threshold is not sacred, but the architecture must produce a broad and convincing improvement. A result such as `loops ~1.5s -> ~0.4-0.6s` together with a large reduction in the Callgrind string-processing signature would strongly justify continuing. A result such as `1.5s -> 1.4s` would not.

Later checkpoints should judge the AST on broad effects, not one cherry-picked benchmark.

## JSON success criteria

JSON should be treated as a first-class Nift strength. The campaign should:

1. quantify raw JSONIC++ performance on identical fixtures;
2. explain the complete delta between JSONIC++ and Nift `inject()`;
3. remove avoidable copies/conversions/bridge overhead;
4. distinguish parse, traverse, mutate, query, transform and serialize;
5. preserve Nift's structured-data semantics;
6. compare against Python/Ruby/Lua/LuaJIT/Node only on equivalent work.

If Nift remains far behind after this decomposition, the remaining gap must be explained rather than accepted as “interpreter overhead.”

## Commit discipline

Commit at the end of each completed checkpoint. A checkpoint that produces only evidence/docs still gets its own commit if it changes the repository. Do not combine unrelated checkpoints merely to reduce commit count. If a prototype fails a go/no-go gate and is reverted, preserve the evidence in the handover/benchmark repository while leaving production code clean.

- Five external `/usr/bin/time` runs each were 0.05/0.06/0.07/0.06/0.05 s (baseline) versus 0.06/0.04/0.06/0.05/0.05 s (CP29): both median ~0.06/0.05 s and within shell/process noise.

### CP31 execution note — raw JSONIC++ baseline
Using the exact 2,188,895-byte / 100,000-record `records-large.json` fixture and an `-O2` C++ harness calling Nift's `nift_json::parse` wrapper directly:

- IO: 3.98-4.84 ms (median ~4.25 ms)
- JSONIC++ parse: 32.69-37.65 ms (median ~33.78 ms)
- Parsed value count: 100,000 on every run

This establishes that the previously observed ~0.33 s Nift `inject()` result is not JSONIC++ parser cost: the language path has roughly an order of magnitude of additional overhead to account for in CP32.
The reproducible harness is `benchmarks/json/jsonic_baseline.cpp`.

### CP32 execution note — `inject()` cost accounting
The current Nift path takes ~0.37-0.39 s end-to-end and peaks near 106.8 MiB RSS on the same 2.19 MB fixture, versus ~4.25 ms IO + ~33.78 ms direct JSONIC++ parsing.

Code-path inspection identified the dominant avoidable design cost: `inject()` reads the file and sends the entire JSON source back through `evaluate_expression()`. Before `resolve_direct()` reaches the structured-literal JSON fast path, the generic evaluator performs repeated top-level operator/ternary/safe-access/postfix scans over the full ~2.19 MB source. The JSON parser itself is therefore only ~34 ms of a ~370-390 ms language operation; roughly ~330 ms is Nift evaluator/bridge overhead plus process/output overhead, with repeated whole-source scanning the principal proven architectural cause.

`benchmarks/json/inject_cost.sh` records the reproducible end-to-end measurement. CP33 should bypass generic expression classification when injected content is valid standalone JSON, while retaining expression-file fallback semantics for non-JSON inject sources.

### CP33 execution note — direct JSON `inject()` fast path
`inject()` now attempts Nift's strict JSONIC++ wrapper immediately after reading the dependency. Valid JSON is moved directly into the result and never traverses the generic expression classifier. Non-JSON input retains the legacy expression-file path, including declarations/expressions and expression-valued structured literals.

On the exact 100,000-record fixture, end-to-end `nift run json-parse/large.f` fell from ~0.37-0.39 s to ~0.07 s after warm filesystem cache (first run ~0.09 s), a roughly **5.3x end-to-end improvement**. This is now much closer to the ~34 ms raw JSONIC++ parse floor; remaining process/binding/value overhead is tens rather than hundreds of milliseconds.

Compatibility smokes for inject dependencies, v4.1 language behavior and adversarial v4.2 behavior pass, plus a new fast-path/fallback smoke.

### CP34 execution note — JSON traversal profiling
The `json-traverse/large` workload now completes in ~0.91 s (correct sum 300000) with CP33's ~0.07 s inject fast path, leaving roughly ~0.84 s in Nift-level traversal/execution.

The direct C++/JSONIC++ harness was extended to traverse the same 100,000 records and sum member `v`. Direct `json::Document` array iteration + object member lookup takes only ~3.48-3.75 ms (median ~3.53 ms). Therefore JSONIC++ representation/member access is **not** the traversal bottleneck: Nift is adding roughly two orders of magnitude through script-loop/binding/expression execution.

This workload currently translates script-land `for` back through the legacy template/control evaluator; CP18 added structural AST representation but prepared runtime migration was intentionally deferred. The result strongly predicts that completing prepared `for` execution/member access in the post-CP41 adversarial/runtime pass is the high-leverage traversal fix rather than changing JSONIC++.
