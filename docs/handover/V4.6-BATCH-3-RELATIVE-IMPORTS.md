# v4.6 Batch 3 relative-import ownership completion

## Contract

Path-shaped relative imports resolve exactly once from the source containing
the import. They do not probe that path and then fall back to the process,
consumer, or project root. Bare package names remain package-store imports, and
absolute paths retain their existing host and confinement behavior.

Each imported module now has durable parser-local identity with its normalized
source path, import base, and package root. `module_path` and `package_path` are
deliberately not introduced at this checkpoint. Callable source paths remain
the execution/diagnostic source of truth; lambda creation now records the same
source path instead of leaving it empty.

Ownership follows exported functions, struct methods, lambdas, named callback
values, nested imports, and transitive re-exports. An import performed while a
module lexical environment is active executes in an isolated child environment
and installs exports into the owning module, not the consumer globals. Export
sets validate before installation. Dynamic child struct exports remain an
explicit error rather than weakening the existing module-private struct limit;
module-private async behavior is unchanged.

Independent review hardened four boundaries. Thread/future workers now deep-copy
module environments, bindings, callable owner edges, and lambda owners, preserve
module identities, and continue allocation from the parent's next identity.
Snapshots include an in-progress loading module, so threads and futures started
during module initialization can resolve its qualified callables and current
bindings. One graph-wide value/slot memo preserves shared aliases and location
reference roots/paths across modules and re-exports while isolating the worker
copy from its parent.
Async scheduling disables only the exact owner-qualified callable in that
worker. Package-owned relative imports are canonical/symlink-aware confined.
Package owners carry frozen lock provenance; a delayed import takes a short read
transaction, validates current lock/installed identity, reads the child, and
releases the transaction before executing child code. Changed remote provenance
fails as stale ownership, while unchanged local provenance remains live.
Cycle checks use canonical identity (with practical Windows case normalization).
Finally, failed outer imports roll back descendant module registrations,
prepared-callable entries, lambdas/struct instances, and their identity
allocators before returning an error.

## Verification

`tests/v44_relative_import_ownership_smoke.sh` covers direct and legacy syntax,
consumer-root decoys, missing siblings and resolved diagnostic paths, nested
and Windows-style paths, package-name imports, exported functions/methods/
lambdas/callbacks, transitive callable owners, lexical restoration, child-export
non-leakage, and template build mode. It is wired as
`test-v46-relative-imports`, into `test-v44-packages`, and through
`test-v46-relative-imports-sanitize` for ASan/UBSan/LSan execution.
`tests/v46_import_worker_ownership_smoke.sh` adds same-name module callbacks,
exact async-owner selection, module-initialization threads/futures, cross-module
alias/reference preservation, parent isolation, concurrent worker-local imports,
mutable module isolation, and identity-collision coverage; it is also wired into the v4.5
concurrency and TSAN walls. Package transaction coverage includes delayed
callable imports that reject a completed replacement without holding a lifetime
lock, plus synchronous child package commands and live local sources. The
relative-import smoke covers traversal/symlink escapes and symlink self-cycles.
The persistent parser unit repeats a failed outer-after-child import before a
successful import to guard rollback stability.
