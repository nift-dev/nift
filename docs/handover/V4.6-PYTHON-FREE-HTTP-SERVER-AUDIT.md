# v4.6 Python-free HTTP server — feasibility and architecture (SERVER0)

Status: investigative checkpoint. No production server code changed, the Python
helper backend is untouched, no Nift core change, no unrelated packages touched,
sqlite untouched. Includes a throwaway cross-platform socket proof (http repo
`tests/socket_proof.f`, experimental workflow).

## 1. Current helper responsibility inventory

The Python helper (`nift-packages/http/helper/http_helper.py`, ~2030 lines,
stdlib only) currently owns:

| Responsibility | Detail |
| --- | --- |
| listening socket | create/bind/listen/accept loop |
| HTTP/1.1 parsing | request line, headers, body, limits |
| request normalization | query, forms, cookies, multipart, spooled bodies |
| worker lifecycle | one-shot + persistent pool, timeouts, process groups |
| request/response exchange | exchange dirs, JSON envelopes, atomic rename |
| response serialization | status/headers/cookies, text/json/file/stream bodies |
| keep-alive | currently one request per connection, `Connection: close` |
| chunked streaming | POSIX FIFO + chunked framing (POSIX only) |
| admission control | `max_concurrency`, 503 overload |
| shutdown | graceful drain, forced abort, status/event observability |

The public Nift `http` facade (`src/http.f`, ~600 lines) owns routing, response
builders, backend selection and the worker protocol. The user-facing API is
`http.server({...})`, `http.get/post/.../route(app, path, handler)`, response
builders, `http.listen(app)`.

## 2. POSIX socket FFI feasibility — VALIDATED

A throwaway proof (`http/tests/socket_proof.f`) uses only the current Nift FFI
against `libc.so.6` / `libSystem.B.dylib` / `ws2_32.dll` to:

```text
socket() -> bind() -> getsockname() -> listen()
client socket() -> connect()
accept() -> send() -> recv() -> close()/closesocket()
```

It passes on **Linux, macOS and Windows** (experimental package workflow run
`37143311856`, all green). Exact FFI facts discovered:

- `socket`/`accept` return a handle: declared `i64(...)`. On x86-64 this reads
  the full register safely (POSIX int is sign-extended; Windows `SOCKET` is
  `UINT_PTR` = 8 bytes). Caveats: on AArch64 a failed POSIX `socket()` returns
  `int -1` zero-extended to `0xFFFFFFFF`, so the proof's `fd < 0` check would
  not detect failure; on 32-bit Windows `UINT_PTR` is 4 bytes. Both are
  unverified (CI is x64); the audit's blanket "a 64-bit read is safe" holds
  only on x86-64. `int`-returning calls (`recv`, `send`, `bind`, `listen`,
  `getsockname`, `WSAStartup`) should use `i32` returns, `i64` only for
  `SOCKET`-returning calls.
- `sockaddr_in` is built as a 16-byte `bytes` value
  `[family u16 LE, port u16 BE, addr u32 BE, 8 pad]` and passed via
  `ffi_buffer`. C writes to `ffi_buffer` are visible via `ffi_bytes`.
- `socklen_t*` out-params are 4-byte buffers that MUST be pre-initialised to
  `16` (little-endian) before `getsockname`/`accept`, otherwise the call fails
  with `EINVAL`.
- `recv`/`send`: `"i64(i64,buffer,i64,i32)"` — buffer is the live byte area,
  the returned count is the byte count; `ffi_bytes` reads the received bytes.
- `close`/`closesocket`: `"i32(i64)"`.
- No variadic calls, no callbacks, no userdata, no `curl_slist`-style lists are
  needed for the socket layer. The libcurl FFI blockers do not apply.
- `poll(struct pollfd*, nfds, timeout)`: POSIX `struct pollfd` is `[int fd,
  short events, short revents]` = 8 bytes on LP64 and is expressible as a
  `bytes` buffer. Windows has no `poll`; the event loop must use `WSAPoll`,
  whose `WSAPOLLFD` is `[SOCKET fd (8 bytes on x64), short events, short
  revents]` = 16 bytes on x64. **The layouts differ per platform and the
  Windows one is unverified by the proof** (it never calls WSAPoll); SERVER2
  must pin the WSAPOLLFD layout on Windows before building the poll buffer.
- `fcntl(fd, F_SETFL, O_NONBLOCK)` is technically variadic (works in practice
  with three fixed args on SysV/AAPCS64 integer registers, but untested), and
  non-blocking mode on Windows is `ioctlsocket`, not `fcntl`. `setsockopt`/
  `getsockopt`/`SO_ERROR`/`WSAGetLastError` are fixed-arity but were reasoned,
  not executed, by the proof.

Remaining FFI wrinkles (not blockers):

- **POSIX `errno` is not directly readable**: FFI cannot dereference the
  pointer returned by `__errno_location()`/`errno` (confirmed: no pointer-deref
  primitive exists). `getsockopt(SOL_SOCKET, SO_ERROR)` covers async/connect
  errors only — a failed `bind`/`accept` (e.g. `EADDRINUSE`, `EMFILE`) is not
  reliably mirrored there. Windows error access is trivial
  (`WSAGetLastError()` is a direct zero-arg call).
- `strerror(errno)` is unusable without `errno`; use package-level stable error
  codes instead of per-errno strings.

## 3. Winsock FFI feasibility — VALIDATED

Windows (x64 — 32-bit Windows is unverified) uses the same pattern:
`WSAStartup(0x0202=514, wsadata_buffer)` (the buffer must be ≥ 408 bytes; the
proof allocates 512), `socket`/`bind`/`listen`/`accept`/`recv`/`send`/
`closesocket`, and `WSACleanup()` (zero args — the proof initially passed a
stray 0 and the FFI signature-count check correctly rejected it). On x64,
`SOCKET` is `UINT_PTR` (8 bytes); `INVALID_SOCKET == -1` as a signed i64, so
`< 0` checks work. Non-blocking mode is `ioctlsocket`, and the event loop uses
`WSAPoll` (layout caveat in §4), not POSIX `poll`/`fcntl`.

## 4. Struct/buffer layout findings

- FFI has no by-value struct calls and `ffi_struct` rejects pointer fields, but
  `ffi_buffer(bytes)` provides a mutable `void*` that C can write, read back via
  `ffi_bytes`, and which stays valid for the duration of the enclosing
  `ffi_call`. This is sufficient for every socket call in the proof.
- Alignment/padding: `sockaddr_in` is 16 bytes on all three platforms.
  `struct pollfd` is 8 bytes on LP64 Linux/macOS; `WSAPOLLFD` on Windows is
  `[SOCKET fd (8 bytes on x64), short events, short revents]` = 16 bytes on x64
  (verified to be a different layout; not executed by the proof).

## 5. Socket/net package recommendation

A reusable low-level package is the right home for the FFI:

```text
nift-packages/socket (or net)
    listener := socket.listen({host, port, backlog})
    conn := listener.accept()
    conn.recv(max_bytes) -> bytes
    conn.send(bytes)
    conn.close() / listener.close()
    conn.poll(...) / non-blocking modes
```

It must hide `libc`/`ws2_32.dll`, `sockaddr_in` layout, `socklen_t`, errno/WSA
differences, and handle width from `http`. It should be **package-level FFI**
(no core change); the proof demonstrates the FFI is sufficient.

## 6. Concurrency design — the real constraint

The curl-client audit found worker closures cannot capture **struct facades**
(`unknown value or malformed expression: curl`; passing one yields
`non-transferable resource`). The same applies to the `http` facade. Route
handlers are user lambdas that reference `http.text()` etc., so they cannot run
on a `thread()` worker either.

Consequences for the native server:

- **Option A1 — single-threaded poll event loop (recommended for the first
  native backend).** Non-blocking sockets + `poll()`/`WSAPoll()` on the main
  thread inside `listen()`. Route handlers run on the main thread. One
  connection is admitted at a time (`max_concurrency = 1`), matching the
  helper's default. Connections are served as non-blocking state machines with
  per-connection poll deadlines (`client_timeout_ms`); a slow client must not
  block the loop — a blocking `recv`/`send` on the main thread would freeze
  the whole server, so all reads/writes are poll-gated.
- **Option A2 — plain-map connection handles + threads.** Plain maps ARE
  capturable by worker closures (verified: a `thread` closure over a map works).
  If `socket` exposes connection handles as plain maps (not a struct facade),
  a per-connection thread could recv/dispatch. But dispatch still needs the
  `http` facade (a struct), which is not capturable — so handler execution
  would still be restricted unless handlers avoid the facade.
- **Option C — tiny C socket/server shim (the user's "C ABI companion"
  pattern).** A 200–1000 line C++ shim (`libnift_sock.so/.dylib/.dll`) exposing
  fixed-arity `accept/recv/send/poll` could also own the event loop natively.
  This is the fallback if pure-FFI concurrency proves limiting, and is the
  preferred general pattern for awkward C APIs (e.g. the future libcurl client).
  For the server it is **not required** by the proof, but it would make a
  native accept/select loop and per-connection threads trivially safe.

Recommended first backend: **single-threaded poll event loop (A1)**, documented
`max_concurrency = 1` for the native backend, with thread/higher-concurrency as
a later decision (either core transferability or the C shim).

## 7. HTTP/1.1 parser feasibility

Nift's string/bytes primitives are sufficient to replicate the Python helper's
parser and limits in the `http` package:

- request line (8 KiB default) and method-token validation
- target/path/query parsing
- header parsing, duplicate handling, lowercasing
- `Content-Length` (single, integer, 1 MiB body default)
- `Transfer-Encoding` rejection (helper rejects it; native must too)
- keep-alive: first backend uses one request per connection, `Connection:
  close` — identical to the current contract
- `Expect: 100-continue`: not currently supported by the helper; defer
- malformed framing, conflicting `Content-Length`, control bytes → bounded 4xx

Intentional reductions vs the helper must be documented; the goal is parity,
not a subset.

## 8. Response writer

Direct socket send of: status line, headers (repeated `Set-Cookie`), then body.
`Content-Length` or chunked framing written in Nift. HEAD suppresses body;
204/205/304 suppress body. Text/JSON via existing builders; binary via `bytes`.
`http.file()`/`http.file_from()` would stream the file through the socket
(package-level read loop) instead of the helper's `sendfile`.

## 9. Streaming

Sockets may make `http.stream()` simpler than the current FIFO: the producer
writes chunks directly to the connection socket with chunked framing in Nift.
On the single-threaded event loop, a long producer blocks the loop (same as the
helper's per-worker blocking). Windows streaming becomes feasible (the current
FIFO is POSIX-only). Not removed merely to remove Python.

## 10. TLS boundary

Not implemented in SERVER0. Plain HTTP on localhost, deployed behind nginx/
Caddy/Traefik, matches the current helper (no TLS). Future: reverse proxy, an
OpenSSL package, or platform TLS — never hand-rolled.

## 11. Security/adversarial requirements

The native backend must replicate the helper's protections:

- CRLF/header injection rejection; malformed request lines → bounded 4xx
- request-smuggling classes: reject `Transfer-Encoding`, conflicting
  `Content-Length`, duplicate framing
- oversized request line / header section / body / headers count
- slow clients: `client_timeout_ms` read deadline via `poll`
- overload/backlog: bounded accept + 503 admission rejection
- multipart bounds and spool-file lifetime; temp-path safety
- connection cleanup and shutdown races (atomics/signals)

## 13. Architecture recommendation

**A. Pure package solution (recommended, validated).**

```text
http package (native backend)
    ↓
socket/net package (FFI to libc/Winsock)
    ↓
Nift FFI (existing)
```

No Nift core change is required for the socket layer (proven). The concurrency
ceiling is `max_concurrency = 1` on a single-threaded poll loop unless the
threading/transferability question is resolved (core change or C shim).

**B. Small general-purpose FFI enhancement** (variadic calls, pointer
dereference for `errno`, richer callbacks) would help `strerror`/`errno` and
future libcurl FFI, but is **not required** for the native server.

**C. Core socket primitive** — not justified; FFI is sufficient.

**D. Python helper retained** — the fallback if native parity proves
costlier than expected.

## 14. Exact core blockers

- **None** for basic POSIX/Winsock sockets (proven by the proof).
- **`errno` not readable** on POSIX (FFI cannot dereference `errno`'s
  address); socket errors remain recoverable via return codes + `SO_ERROR`.
- **Worker closures cannot capture struct facades**: caps concurrency to 1 on
  a single-threaded loop, or requires the C shim / a core transferability
  change for thread-per-connection. This is the same limitation the curl audit
  found; it is a general Nift question, not an HTTP-server defect.

## 14b. Verified vs reasoned claims

Executed by the proof (Linux/macOS/Windows): `socket`/`bind`/`getsockname`/
`listen`/`connect`/`accept`/`send`/`recv`/`close`/`closesocket`, `WSAStartup`,
`WSACleanup`, the `sockaddr_in` layout, `ffi_buffer` in/out and `ffi_bytes`
read-back, the `socklen_t` pre-init to 16.

Reasoned but NOT executed by the proof: `poll`/`WSAPoll` (and the WSAPOLLFD
layout), `fcntl`/`ioctlsocket` non-blocking mode, `setsockopt`/`getsockopt`/
`SO_ERROR`, `WSAGetLastError`, route handlers on `thread()` workers, the HTTP
parser and poll-deadline mechanisms. SERVER1/SERVER2 must exercise each before
relying on it. The proof is a throwaway: it does not early-exit on a failed
call (failures are counted, and the unconditional closes still run), which is
acceptable for feasibility but must not be copied into production.

```text
SERVER0  this audit + cross-platform socket proof          (DONE)
SERVER1  reusable socket/net package (FFI, poll, plain-map handles)
SERVER2  minimal native HTTP/1.1 backend in http package
         (single-threaded poll loop, one request per connection)
SERVER3  routing/request parity (params, JSON/text, cookies)
SERVER4  forms/cookies/uploads/body limits, spool lifetime
SERVER5  concurrency/admission (max_concurrency, 503)
SERVER6  streaming/chunked responses via sockets
SERVER7  graceful shutdown/adversarial hardening
SERVER8  Linux/macOS/Windows certification
SERVER9  remove the Python helper + production Python dependency
```

## 16. Compatibility / migration

- The public `http` facade API is preserved; the backend selection gains a
  native backend alongside `process`.
- Existing 16 package-local Python harnesses are the reference contract; the
  Python helper stays until SERVER9.
- `capabilities()` truthfully reports the native backend's limits (e.g.
  concurrency, streaming on Windows).
