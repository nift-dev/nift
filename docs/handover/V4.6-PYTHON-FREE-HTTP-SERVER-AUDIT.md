# v4.6 Python-free HTTP server — feasibility and architecture (SERVER0)

Status: investigative checkpoint. No production server code changed, the Python
helper backend is untouched, no Nift core change, no unrelated packages touched,
sqlite untouched. Includes a throwaway cross-platform socket proof (http repo
`tests/socket_proof.f`, experimental workflow).

## 1. Current helper responsibility inventory

The Python helper (`nift-packages/http/helper/http_helper.py`, ~2030 lines,
stdlib only) currently owns:

| Responsibility | Detail |
| --- | --- |
| listening socket | create/bind/listen/accept loop |
| HTTP/1.1 parsing | request line, headers, body, limits |
| request normalization | query, forms, cookies, multipart, spooled bodies |
| worker lifecycle | one-shot + persistent pool, timeouts, process groups |
| request/response exchange | exchange dirs, JSON envelopes, atomic rename |
| response serialization | status/headers/cookies, text/json/file/stream bodies |
| keep-alive | currently one request per connection, `Connection: close` |
| chunked streaming | POSIX FIFO + chunked framing (POSIX only) |
| admission control | `max_concurrency`, 503 overload |
| shutdown | graceful drain, forced abort, status/event observability |

The public Nift `http` facade (`src/http.f`, ~600 lines) owns routing, response
builders, backend selection and the worker protocol. The user-facing API is
`http.server({...})`, `http.get/post/.../route(app, path, handler)`, response
builders, `http.listen(app)`.

## 2. POSIX socket FFI feasibility — VALIDATED

A throwaway proof (`http/tests/socket_proof.f`) uses only the current Nift FFI
against `libc.so.6` / `libSystem.B.dylib` / `ws2_32.dll` to:

```text
socket() -> bind() -> getsockname() -> listen()
client socket() -> connect()
accept() -> send() -> recv() -> close()/closesocket()
```

It passes on **Linux, macOS and Windows** (experimental package workflow run
`37143311856`, all green). Exact FFI facts discovered:

- `socket`/`accept` return a handle: declared `i64(...)`. On x86-64 this reads
  the full register safely (POSIX int is sign-extended; Windows `SOCKET` is
  `UINT_PTR` = 8 bytes). Caveats: on AArch64 a failed POSIX `socket()` returns
  `int -1` zero-extended to `0xFFFFFFFF`, so the proof's `fd < 0` check would
  not detect failure; on 32-bit Windows `UINT_PTR` is 4 bytes. Both are
  unverified (CI is x64); the audit's blanket "a 64-bit read is safe" holds
  only on x86-64. `int`-returning calls (`recv`, `send`, `bind`, `listen`,
  `getsockname`, `WSAStartup`) should use `i32` returns, `i64` only for
  `SOCKET`-returning calls.
- `sockaddr_in` is built as a 16-byte `bytes` value
  `[family u16 LE, port u16 BE, addr u32 BE, 8 pad]` and passed via
  `ffi_buffer`. C writes to `ffi_buffer` are visible via `ffi_bytes`.
- `socklen_t*` out-params are 4-byte buffers that MUST be pre-initialised to
  `16` (little-endian) before `getsockname`/`accept`, otherwise the call fails
  with `EINVAL`.
- `recv`/`send`: `"i64(i64,buffer,i64,i32)"` — buffer is the live byte area,
  the returned count is the byte count; `ffi_bytes` reads the received bytes.
- `close`/`closesocket`: `"i32(i64)"`.
- No variadic calls, no callbacks, no userdata, no `curl_slist`-style lists are
  needed for the socket layer. The libcurl FFI blockers do not apply.
- `poll(struct pollfd*, nfds, timeout)`: POSIX `struct pollfd` is `[int fd,
  short events, short revents]` = 8 bytes on LP64 and is expressible as a
  `bytes` buffer. Windows has no `poll`; the event loop must use `WSAPoll`,
  whose `WSAPOLLFD` is `[SOCKET fd (8 bytes on x64), short events, short
  revents]` = 16 bytes on x64. **The layouts differ per platform and the
  Windows one is unverified by the proof** (it never calls WSAPoll); SERVER2
  must pin the WSAPOLLFD layout on Windows before building the poll buffer.
- `fcntl(fd, F_SETFL, O_NONBLOCK)` is technically variadic (works in practice
  with three fixed args on SysV/AAPCS64 integer registers, but untested), and
  non-blocking mode on Windows is `ioctlsocket`, not `fcntl`. `setsockopt`/
  `getsockopt`/`SO_ERROR`/`WSAGetLastError` are fixed-arity but were reasoned,
  not executed, by the proof.

Remaining FFI wrinkles (not blockers):

- **POSIX `errno` is not directly readable**: FFI cannot dereference the
  pointer returned by `__errno_location()`/`errno` (confirmed: no pointer-deref
  primitive exists). `getsockopt(SOL_SOCKET, SO_ERROR)` covers async/connect
  errors only — a failed `bind`/`accept` (e.g. `EADDRINUSE`, `EMFILE`) is not
  reliably mirrored there. Windows error access is trivial
  (`WSAGetLastError()` is a direct zero-arg call).
- `strerror(errno)` is unusable without `errno`; use package-level stable error
  codes instead of per-errno strings.

## 3. Winsock FFI feasibility — VALIDATED

Windows (x64 — 32-bit Windows is unverified) uses the same pattern:
`WSAStartup(0x0202=514, wsadata_buffer)` (the buffer must be ≥ 408 bytes; the
proof allocates 512), `socket`/`bind`/`listen`/`accept`/`recv`/`send`/
`closesocket`, and `WSACleanup()` (zero args — the proof initially passed a
stray 0 and the FFI signature-count check correctly rejected it). On x64,
`SOCKET` is `UINT_PTR` (8 bytes); `INVALID_SOCKET == -1` as a signed i64, so
`< 0` checks work. Non-blocking mode is `ioctlsocket`, and the event loop uses
`WSAPoll` (layout caveat in §4), not POSIX `poll`/`fcntl`.

## 4. Struct/buffer layout findings

- FFI has no by-value struct calls and `ffi_struct` rejects pointer fields, but
  `ffi_buffer(bytes)` provides a mutable `void*` that C can write, read back via
  `ffi_bytes`, and which stays valid for the duration of the enclosing
  `ffi_call`. This is sufficient for every socket call in the proof.
- Alignment/padding: `sockaddr_in` is 16 bytes on all three platforms.
  `struct pollfd` is 8 bytes on LP64 Linux/macOS; `WSAPOLLFD` on Windows is
  `[SOCKET fd (8 bytes on x64), short events, short revents]` = 16 bytes on x64
  (verified to be a different layout; not executed by the proof).

## 5. Socket/net package recommendation

A reusable low-level package is the right home for the FFI:

```text
nift-packages/socket (or net)
    listener := socket.listen({host, port, backlog})
    conn := listener.accept()
    conn.recv(max_bytes) -> bytes
    conn.send(bytes)
    conn.close() / listener.close()
    conn.poll(...) / non-blocking modes
```

It must hide `libc`/`ws2_32.dll`, `sockaddr_in` layout, `socklen_t`, errno/WSA
differences, and handle width from `http`. It should be **package-level FFI**
(no core change); the proof demonstrates the FFI is sufficient.

## 6. Concurrency design — the real constraint

The curl-client audit found worker closures cannot capture **struct facades**
(`unknown value or malformed expression: curl`; passing one yields
`non-transferable resource`). The same applies to the `http` facade. Route
handlers are user lambdas that reference `http.text()` etc., so they cannot run
on a `thread()` worker either.

Consequences for the native server:

- **Option A1 — single-threaded poll event loop (recommended for the first
  native backend).** Non-blocking sockets + `poll()`/`WSAPoll()` on the main
  thread inside `listen()`. Route handlers run on the main thread. One
  connection is admitted at a time (`max_concurrency = 1`), matching the
  helper's default. Connections are served as non-blocking state machines with
  per-connection poll deadlines (`client_timeout_ms`); a slow client must not
  block the loop — a blocking `recv`/`send` on the main thread would freeze
  the whole server, so all reads/writes are poll-gated.
- **Option A2 — plain-map connection handles + threads.** Plain maps ARE
  capturable by worker closures (verified: a `thread` closure over a map works).
  If `socket` exposes connection handles as plain maps (not a struct facade),
  a per-connection thread could recv/dispatch. But dispatch still needs the
  `http` facade (a struct), which is not capturable — so handler execution
  would still be restricted unless handlers avoid the facade.
- **Option C — tiny C socket/server shim (the user's "C ABI companion"
  pattern).** A 200–1000 line C++ shim (`libnift_sock.so/.dylib/.dll`) exposing
  fixed-arity `accept/recv/send/poll` could also own the event loop natively.
  This is the fallback if pure-FFI concurrency proves limiting, and is the
  preferred general pattern for awkward C APIs (e.g. the future libcurl client).
  For the server it is **not required** by the proof, but it would make a
  native accept/select loop and per-connection threads trivially safe.

Recommended first backend: **single-threaded poll event loop (A1)**, documented
`max_concurrency = 1` for the native backend, with thread/higher-concurrency as
a later decision (either core transferability or the C shim).

## 7. HTTP/1.1 parser feasibility

Nift's string/bytes primitives are sufficient to replicate the Python helper's
parser and limits in the `http` package:

- request line (8 KiB default) and method-token validation
- target/path/query parsing
- header parsing, duplicate handling, lowercasing
- `Content-Length` (single, integer, 1 MiB body default)
- `Transfer-Encoding` rejection (helper rejects it; native must too)
- keep-alive: first backend uses one request per connection, `Connection:
  close` — identical to the current contract
- `Expect: 100-continue`: not currently supported by the helper; defer
- malformed framing, conflicting `Content-Length`, control bytes → bounded 4xx

Intentional reductions vs the helper must be documented; the goal is parity,
not a subset.

## 8. Response writer

Direct socket send of: status line, headers (repeated `Set-Cookie`), then body.
`Content-Length` or chunked framing written in Nift. HEAD suppresses body;
204/205/304 suppress body. Text/JSON via existing builders; binary via `bytes`.
`http.file()`/`http.file_from()` would stream the file through the socket
(package-level read loop) instead of the helper's `sendfile`.

## 9. Streaming

Sockets may make `http.stream()` simpler than the current FIFO: the producer
writes chunks directly to the connection socket with chunked framing in Nift.
On the single-threaded event loop, a long producer blocks the loop (same as the
helper's per-worker blocking). Windows streaming becomes feasible (the current
FIFO is POSIX-only). Not removed merely to remove Python.

## 10. TLS boundary

Not implemented in SERVER0. Plain HTTP on localhost, deployed behind nginx/
Caddy/Traefik, matches the current helper (no TLS). Future: reverse proxy, an
OpenSSL package, or platform TLS — never hand-rolled.

## 11. Security/adversarial requirements

The native backend must replicate the helper's protections:

- CRLF/header injection rejection; malformed request lines → bounded 4xx
- request-smuggling classes: reject `Transfer-Encoding`, conflicting
  `Content-Length`, duplicate framing
- oversized request line / header section / body / headers count
- slow clients: `client_timeout_ms` read deadline via `poll`
- overload/backlog: bounded accept + 503 admission rejection
- multipart bounds and spool-file lifetime; temp-path safety
- connection cleanup and shutdown races (atomics/signals)

## 13. Architecture recommendation

**A. Pure package solution (recommended, validated).**

```text
http package (native backend)
    ↓
socket/net package (FFI to libc/Winsock)
    ↓
Nift FFI (existing)
```

No Nift core change is required for the socket layer (proven). The concurrency
ceiling is `max_concurrency = 1` on a single-threaded poll loop unless the
threading/transferability question is resolved (core change or C shim).

**B. Small general-purpose FFI enhancement** (variadic calls, pointer
dereference for `errno`, richer callbacks) would help `strerror`/`errno` and
future libcurl FFI, but is **not required** for the native server.

**C. Core socket primitive** — not justified; FFI is sufficient.

**D. Python helper retained** — the fallback if native parity proves
costlier than expected.

## 14. Exact core blockers

- **None** for basic POSIX/Winsock sockets (proven by the proof).
- **`errno` not readable** on POSIX (FFI cannot dereference `errno`'s
  address); socket errors remain recoverable via return codes + `SO_ERROR`.
- **Worker closures cannot capture struct facades**: caps concurrency to 1 on
  a single-threaded loop, or requires the C shim / a core transferability
  change for thread-per-connection. This is the same limitation the curl audit
  found; it is a general Nift question, not an HTTP-server defect.

### Exported API and handle representation

```text
socket.listen({host, port, backlog}) -> {ok, handle, port, error_code}
socket.accept(listener)              -> {ok, conn, would_block, ...}
socket.connect({host, port})         -> {ok, conn, error_code}   // blocking
socket.recv(conn, max)               -> {ok, data(bytes), eof, would_block, error_code}
socket.send(conn, data) / send_all   -> {ok, sent, would_block, ...}
socket.shutdown / socket.close
socket.local_address / peer_address  -> {ok, host, port}
socket.poll([handles], timeout_ms)   -> [{handle, readable, writable, error, hangup}]
```

Handles are plain transferable maps `{kind, fd, _id}` (not struct facades), so
they can cross worker boundaries later. Every handle is non-blocking;
`recv`/`accept`/`send` are poll-gated first so `would_block` is deterministic.
`connect` is intentionally blocking and documented (the server side never
calls connect).

### POSIX / Winsock implementation

- POSIX: `socket/bind/listen/accept/recv/send/close/fcntl/poll/getsockname/
  getpeername` via `libc`/`libSystem`. Non-blocking via `fcntl(F_SETFL,
  O_NONBLOCK)` (O_NONBLOCK 2048 Linux / 4 macOS). `pollfd` built as a byte
  buffer (`int fd`, `short events`, `short revents`).
- Windows x64: `WSAStartup` (once, process-lifetime, return checked),
  `socket/bind/listen/accept/recv/send/closesocket/ioctlsocket(FIONBIO)`,
  `WSAGetLastError`. Readiness uses Winsock **`select()`** (manually-built
  `fd_set`: fd_count + 8-byte `SOCKET` array, 520 bytes) instead of `WSAPoll`,
  which was intermittently failing with WSAEINVAL on the hosted runner;
  `socket.poll` caps at 64 handles (FD_SETSIZE).
- `recv`/`send` use `i32` returns on Windows (`int`) and `i64` on POSIX
  (`ssize_t`); `SOCKET`-returning calls use `i64`.

### Binary contract / errors / lifecycle

- Binary-safe: request/response bytes exact through `ffi_buffer`/`ffi_bytes`;
  a 16 KiB all-octet roundtrip is certified.
- Stable error codes: `address_in_use`, `connection_refused`,
  `connection_reset`, `would_block`, `invalid_address`, `invalid_handle`,
  `socket_error`. POSIX `errno` is not surfaced (documented FFI limit);
  `would_block` is classified with a zero-timeout poll heuristic.
- `close` deregisters then closes; double close is `invalid_handle`. Windows
  uses `closesocket`; `WSACleanup` is never called (no cleanup race).
- IPv4 numeric hosts only; IPv6 and DNS deferred.

### Independent review

A separate review found no blockers. Two majors were repaired:
(1) the only non-poll-gated call (`connect`) was made blocking and is now
documented — a non-blocking connect (poll-writability + `getpeername`/
`SO_ERROR`) is deferred; (2) Winsock `select()` was passed the same buffer for
readfds and exceptfds (aliasing-dependent) — now a distinct empty exceptfds
buffer. Minors repaired: 64-bit SOCKET truncation in fd_sets (le64), truthful
`writable` from `socket.poll` (POLLIN|POLLOUT), a dead WSAPoll branch removed,
Windows >64-handle cap, WSAStartup return checked, and test gaps closed (a
fresh listener reports `readable=false`; 16 KiB binary roundtrip).

## SERVER2 — minimal native HTTP/1.1 backend (BLOCKED by Nift core bugs)

SERVER2 began the first production Python-replacement work. Deliverable #1 is
done: `nift-packages/http` now declares a real Batch-5 dependency on `socket`
(`{"dependencies":{"socket":{"source":"socket","ref":"latest"}}}`). E2E
verified: `nift add http` installs/resolves `socket` transitively and the v2
lock contains both nodes with the correct edge (socket pinned to `4d96f49`).
The Python process backend is untouched and green.

The native backend implementation is **blocked by Nift core string-handling
bugs**. A full native backend was drafted (event loop over `sock_*`, bounded
HTTP/1.1 parser, response writer) and incrementally debugged on Linux. The
request parser cannot be written cleanly in the current language because:

1. **`str.substr(i,1).encode("utf-8")` fails on function/method parameters.**
   Iterating a parameter string char-by-char (`c := s.substr(i,1)` then
   `c.encode("utf-8")[0]`) raises `encode: encoding must be exactly 'utf-8'`,
   while the identical loop over a local variable works. Workaround: encode the
   whole string once (`b := s.encode("utf-8")`) and index `b[i]` — this works,
   but reveals the next bug.

2. **`reference target no longer exists` when calling a helper method from the
   http package parser.** With the whole-string-encode workaround,
   `this.token_ok(method)` (and even `this.token_ok("GET")` with a literal)
   raises `reference target no longer exists` inside the http package's
   `parse_request`, while the same minimal struct method call works in
   isolation. This is a string memory-lifetime bug in the large package.

3. **Cross-package facade limitation.** A package cannot invoke another
   package's exported struct facade (`struct type is not available in this
   scope: socket`). A socket refactor exposing self-contained top-level
   `sock_*` functions works cross-package, but was reverted to keep SERVER1's
   reviewed state frozen (documented here for the later core fix).

Other Nift quirks confirmed during SERVER2: `return` inside a `for` in a
struct method does not return; map-literal string concatenation is not
evaluated; `{}` objects do not support `.set()` (bracket assignment only);
`"".encode("utf-8")` errors; plain-map member assignment needs brackets.

**Recommendation:** a small, general-purpose Nift core fix for string
parameter/method-call lifetime safety (and reliable per-char access) is
required before the pure-Nift native HTTP server is feasible. This is a
general string-handling fix benefiting any parsing package, not an HTTP hack.
SERVER2 resumes after that fix.

## CORE-SERVER-BLOCKERS — Nift correctness checkpoint (resolves the SERVER2 blockers)

The SERVER2 blocker was investigated under a focused core checkpoint. Root causes
were classified separately and fixed as general language correctness repairs:

1. **Cross-package exported facade dispatch (primary blocker).** Root cause:
   struct-method dispatch resolved the StructDefinition from the parser-global
   `structs_` registry by bare type name. A package's functions (or another
   package) could only dispatch on a facade if its type happened to be
   registered globally. Fixed by storing the StructDefinition on each
   StructInstance and resolving dispatch through the instance, attaching the
   module environment to facade definitions at export so methods resolve the
   module's private bindings. This makes `package B -> package A exported
   facade` work (the Batch 5 `http -> socket` API-composition layer). Private
   facade types are not constructible by importers; two modules defining the
   same type name dispatch correctly per-module.
2. **`reference target no longer exists` on `c := b[0]` (bytes index) in a
   loop body.** The AST hot-path `bind_location` errored when a location
   reference did not resolve to a referenceable aggregate instead of falling
   back to the plain value binding (matching the string-eval path). Bytes have
   no aliased location; array/object indexes worked. Fixed to fall back.
3. **Object-literal values preserved as text.** `{"a": "pre " + x + " post"}`
   was treated as a literal whenever the value started and ended with a quote.
   Now a value is a literal only when it is one fully-quoted string; embedded
   unescaped quotes fall back to the literal interpretation if eval fails.
4. **Audited but no defect:** the Batch 4 `ast_context()` cached Context
   (ParserTemplate.cpp) was not implicated; the lifetime symptoms were the
   bytes-index binding path and the package type-registry path above.
   `return` inside `for` exits the callable in all contexts (pinned by tests).
   Empty-string UTF-8 encode/decode return empty values (pinned).

Reproduction/regression wall: `tests/core_language_correctness.sh` pins
object-literal expression values, empty-string codecs, return-exits-callable,
cross-package facade + private-facade dispatch, and bytes-index bindings in
loop bodies.

Core commits (on `96cd3ec`):
- `07a0dc6` fix: evaluate object-literal string-concat values as expressions
- `5f19155` fix: register module struct types when exporting callables
  (approach superseded by `02480c4` after independent review found a same-name
  type collision could misdispatch across modules)
- `edf6099` fix: bytes-index binding in loop bodies must fall back to a value
- `02480c4` fix: dispatch struct methods via the instance's own definition
- `ca2fd48` fix: object literals with embedded unescaped quotes keep parsing

Certification: full relevant gate green (v41-v45 language/package/execution/
concurrency/job-control/native-runtime/adversarial, recovery-epoch, host-seam,
c-abi, ffi-abi, json, json-binding, control-flow); ASan/UBSan and TSan clean on
the focused reproductions and the regression wall; 1M-integer-loop runtime
0.62-0.63s (no Batch 4 hot-path regression). Independent review performed; its
MAJOR finding (cross-module type-name collision) was fixed by `02480c4` and
its MINOR findings (private-type constructibility, module-callable import,
embedded-quote regression) were all verified resolved.

SERVER2 can resume from the clean `9751d1a` http base: the native backend can
now call `socket`'s exported facade from package code, dispatch private helper

## SERVER2-R — native HTTP/1.1 backend (delivered on the fixed runtime)

The CORE-SERVER-BLOCKERS fixes unblocked the pure-Nift native HTTP backend.
The opt-in backend was reimplemented cleanly in `nift-packages/http` against
the fixed runtime (cross-package facade dispatch via instance-carried
definitions, bytes-index value bindings, evaluated object literals).

**Backend:** `http.use_backend("native")` selects it; process backend remains
the default oracle and is unchanged. The native backend calls the `socket`
package facade directly (listen/accept/poll/recv/send_all/close/peer_address)
through the real `http -> socket` transitive dependency. No Python, no shell,
no C/C++ shim, no Nift core change.

**Event loop:** one loop polling the listener plus all active connections;
newly accepted connections survive into the next poll cycle (tracked by fd,
not the pre-accept poll result); stage-aware readiness (read for reading
conns, write for sending conns); per-connection read timeout reaping (408);
connection-reset/eof reaping; all responses flow through a pending/sending
state machine that tracks actual bytes sent (no truncated responses);
`max_concurrency` cap keeps Windows under the 64-handle poll ceiling and a
poll failure is a hard error.

**Parser (bounded HTTP/1.1):** request line 8 KiB, header block 32 KiB, 100
headers, body 1 MiB; rejects bare CR/LF, header obs-fold, non-token names,
invalid UTF-8 header values, duplicate/conflicting/invalid Content-Length,
oversized limits, non-origin targets, malformed request lines, and all
Transfer-Encoding (501). Host required for HTTP/1.1. Malformed percent-escapes
reject (400). Paths decode per-segment (no '+'->space in paths, empty segments
skipped) matching the oracle. GET/HEAD/POST (and any token method), one request
per connection with `Connection: close`.

**Responses:** status line + reason, Content-Length, `Connection: close`,
repeated Set-Cookie, hand-written JSON serializer (escapes/control chars),
text/bytes bodies, HEAD same Content-Length with no body, 204/205/304 no-body.
CRLF rejected in response header names/values and Set-Cookie. Handler/serialize
errors answered 500. `capabilities()` reports the native truth set (no
multipart/streaming/uploads/persistent workers/binary files; forms:false).

**Certification (Linux):** native contract harness 26/26 (route params, HEAD,

## SERVER3-PERF — native event-loop performance checkpoint

Profiled the native request/event loop (local, with the socket buffer cache
from the socket package) and fixed the latency sources found by SERVER-BENCH.

### Profiling results (single GET /text, local)

The ~120 ms request latency decomposed as:

| phase | cost | cause |
|---|---|---|
| recv | ~65-69 ms | `socket.recv(conn, 65536)` built a fresh 64 KiB zero array via `zeros(max)` (interpreted array construction, ~1 us/byte) |
| header parse | ~11 ms | redundant per-byte passes over each header (name validation, lowercasing, value strip/validate/UTF-8, two slices) |
| request-line parse | ~3 ms | interpreted byte parsing |
| dispatch | ~4 ms | route match + handler |
| send | ~3 ms | pending/sending state machine |

The fixed 50 ms event-loop poll was NOT the dominant cost once the recv buffer
was fixed; it bounded idle-to-first-request latency only.

### Fixes (committed)

- **socket package (`5a607df`)** — `recv()` caches one growable receive buffer
  and reuses it, so steady-state recv is allocation-free (the ~65 ms zeros
  build happens once). Genuine SERVER1 defect; socket package is single-threaded
  so a shared buffer adds no race.
- **http native backend (`786142f`)** — request reads use 16 KiB recv chunks
  (smaller ffi_bytes conversion); the header parser merges name validation and
  lowercasing into one pass and slices the value once; the event-loop poll
  timeout is configurable (`poll_timeout_ms`, default 10 ms) so
  idle-to-first-request latency is bounded without a fixed 50 ms stall.
- **http native backend (`c27f241`)** — a sending connection that makes no
  full-chunk send progress for `client_timeout_ms` is reaped. Slow readers
  remain "writable" to poll (the OS send buffer always has room), so the idle
  read-reaping never fired; only full-chunk sends now count as progress.

### Results (local, after fixes)

- Single-request latency: ~120 ms -> ~35 ms median.
- Throughput (native, `tests/benchmark.py`): c=1 18 req/s, c=4 20 req/s,
  c=16 22 req/s, c=32 23 req/s (was ~5 req/s before). Still single-threaded
  bound: each request costs ~20-30 ms of interpreted parsing + dispatch.

### Remaining findings

- **Slowloris fairness:** with > `max_concurrency` partial connections, the
  accept gate blocks, and good clients are starved for up to
  `client_timeout_ms` until the slow connections are reaped. The process
  backend rejects excess admissions instead. This is a SERVER7 hardening item
  (reject excess admissions / shorter slow-read timeout).
- **128 KiB response RSS:** the spike (to ~400+ MB under 20 concurrent
  /large) is dominated by the handler's Nift string concatenation
  (`s += chunk`, O(n^2) allocation churn) reclaimed by the GC, not the
  backend's per-connection pending-send (which is ~128 KiB per connection and
  bounded by the new stall reaping).
- **Head-of-line blocking:** unchanged — the single-threaded loop stalls fast
  routes under sustained slow-handler load (~4x degradation measured in
  SERVER-BENCH). Assessed for the handler-concurrency architecture decision:
  a worker/pool model would be needed to remove it (SERVER5).

### Benchmark harness

`tests/benchmark.py` in nift-packages/http measures native req/s + p50/p95/p99
under sustained concurrent load and treats any run with 2xx == 0 as INVALID
(aborts, never counted). The SERVER-BENCH F_large/G_compute rows that were
error-flood artifacts (2xx == 0) would be rejected by this harness.
