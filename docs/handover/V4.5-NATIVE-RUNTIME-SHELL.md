# Nift v4.5.0 — native runtime, concurrency, FFI and shell campaign

Status: **implemented, certified, and released 2026-09-27**. This document is
the authoritative step-by-step campaign record for Nift v4.5.0. It starts from
the v4.4.0 release plus
the existing `Begin v4.5.0 development` checkpoint and deliberately turns the
Nift language/runtime into a more complete general-purpose scripting environment
without weakening the website-generation/build guarantees that already exist.

The campaign has four primary goals:

1. make Nift a first-class scripting language and interactive shell rather than
   requiring `nift run` / `nift sh` wrapper commands;
2. add real native concurrency: threads, mutexes and `async` / `await` backed by
   actual parallel execution;
3. add a practical native FFI with a stable, testable ownership/type boundary;
4. harden and promote the existing experimental embedding work into a supported
   embeddable Nift scripting/template runtime.

A fifth cross-cutting goal is to finish the intentionally deferred Bash-style job
control story from v4.4 and make platform/target awareness good enough for future
native/mobile/application work.

## Settled v4.5 product decisions

These decisions are accepted unless implementation evidence proves that one is
unsafe or internally contradictory. Do not repeatedly reopen them during the
campaign.

- Remove `nift run <path>` outright. There are no compatibility users to protect.
  `nift <path>` is the script-file invocation syntax.
- Remove `nift sh` outright. Plain `nift` starts the persistent interactive Nift
  shell/REPL.
- CLI dispatch is command-first, then file-path fallback. A known Nift command
  remains a command. Otherwise, if the first positional argument names an
  existing regular file, execute it as a Nift script. If it is neither, fail
  explicitly with an error that says the command is unknown **and** the path does
  not exist. Do not silently reinterpret typos.
- Keep direct shebang execution. It already exists in the v4.5 baseline and must
  be certified rather than reimplemented: `#!/usr/bin/env nift` followed by an
  executable `.f` file must continue to work.
- Named user functions are already first-class callable values in the baseline.
  Preserve and certify them through concurrency/FFI/embedding work rather than
  implementing a second callable mechanism.
- Scripts use `cmd` and `args`, following the Strut convention rather than
  `argc`/`argv`: `cmd` represents the invocation command (`argv[0]` semantics;
  not necessarily a canonical path) and `args` contains only user arguments.
  The existing immutable `args` script binding remains the foundation.
- Keep `getenv`, `setenv` and `unsetenv`; they already exist. Add `env()` if the
  cross-platform implementation can return a safe ordinary Nift map/object of
  the current process environment.
- Add `os()` and `platform()`. `os()` describes the host operating system. `platform()`
  describes the selected build/runtime target and is deliberately distinct from
  the host. Example intended direction: `nift build --platform=android` selects target
  `android`, and `platform()` evaluates to `"android"` while the build executes.
- Prefer `platform()` over `target()` for runtime/build platform selection because `init --target=<provider>` already has an established deployment-provider meaning. Add `arch()` separately if
  architecture introspection is useful; do not overload `platform()` with CPU
  architecture.
- Support stdin as source: piped source and explicit `nift -`, including
  `nift - < script.f`.
- Add conventional inline-code/interactive flags. `-e` is the canonical execute
  spelling; `-c` is an accepted alias. `-i` means remain interactive after the
  supplied file/stdin/inline source executes, preserving the live runtime state.
- Finish real Bash-style job control: background jobs, `jobs`, `fg`, `bg`,
  process groups, terminal handoff, signal handling and `wait` semantics where
  supported by the host OS. Do not fake job control on platforms whose process
  model cannot implement a claimed behavior.
- `async` / `await` must be genuinely parallel-capable. Do not implement a
  JavaScript-style single-threaded event-loop substitute and call it
  multithreading.
- Native `thread` / `mutex` APIs and `async` / `await` must share one coherent
  concurrency/runtime ownership model rather than becoming two unrelated
  schedulers.
- FFI initially targets the C ABI. Cross-platform dynamic libraries are `.so`,
  `.dylib` and `.dll`; richer C++ ABI binding is not a v4.5 requirement.
- The existing `include/nift/`, `src/embed/`, C ABI and language-binding work is
  the starting point for embedding. Reuse and harden it; do not create a second
  embedded runtime beside it.
- The supported embedding story must include both Nift scripting and Nift
  template/rendering use cases. Host applications must be able to inject values,
  expose native functions, execute/evaluate Nift, and receive values/errors back
  without shelling out to the CLI.
- Preserve the v4.4 security/capability distinction. Build safety, `--no-process`,
  filesystem restrictions and embedded-host boundaries must remain explicit.
- Do not add new third-party runtime dependencies casually. Prefer the C++
  standard library, OS APIs and existing Nift-owned/runtime code; any new
  vendored dependency requires deliberate approval and release/distribution
  analysis first.

## Repository-safety and checkpoint rules

These rules apply to **every checkpoint** in this campaign.

- Start each checkpoint from clean working trees in every repository that will be
  touched. Record branch names and `git status --short --branch` before editing.
- Never use destructive Git operations (`reset --hard`, forced checkout over
  unknown work, history rewriting, deleting `.git`, replacing repositories with
  exported copies, or broad cleanup commands) as part of normal checkpoint work.
- Never initialize a new repository inside an existing repository or accidentally
  nest/copy `.git` metadata.
- Do not move or rewrite unrelated files merely to make a diff look clean.
- Preserve existing user/maintainer work. If the checkout is unexpectedly dirty,
  investigate and stop that checkpoint rather than discarding changes.
- Keep changes checkpoint-sized and reviewable. A checkpoint may span the Nift
  source repo, the independent `nift-regression-suite`, and the website repo when
  the public behavior requires all three, but each repository must have its own
  coherent commit.
- Run the checkpoint's focused tests before committing. Run the broader maintained
  wall appropriate to the risk before declaring the checkpoint complete.
- Inspect `git diff --check`, `git diff`, staged diff, and final `git status` in
  every changed repository.
- **Commit at the end of every completed checkpoint.** Do not begin the next
  checkpoint with uncommitted implementation/docs/test work from the previous
  one. If multiple repositories changed, commit all of them before advancing.
- Record the resulting commit IDs in this campaign document as checkpoints are
  completed. The handover itself is living project state, not a detached diary.
- No autonomous push, tag, release, package publication or history rewrite.
  Follow the established release handover and stop for the maintainer at the
  explicit publication gates.
- Keep source tests and the independent regression suite independent enough to
  catch shared mistaken assumptions.
- Add a regression test for every bug found during implementation, review, CI or
  dogfooding before considering the bug fixed.
- Cross-platform claims require Linux/macOS/Windows evidence. Platform-specific
  functionality may be explicitly scoped, but must fail honestly rather than
  pretend parity.

### CP2 — freeze unified invocation semantics

#### Frozen invocation grammar (CP2)

CLI source-selection precedence is:

1. zero positional source/command plus no one-shot option: start the REPL;
2. help/version/completion and other known Nift commands are commands;
3. `-e CODE` / `-c CODE` select inline program source;
4. `-` selects stdin program source;
5. an explicit or bare path that resolves to an existing regular file selects that file;
6. anything else is an error: `unknown command '<token>' and path does not exist`.

Known commands intentionally win over a same-named file in the cwd. To run such a file,
spell it explicitly (`./build`, `./status`, etc.). Directories never count as script files.

`-i` is an execution modifier, not a source: with no source it starts the REPL; with a
file, stdin, `-e`, or `-c` it executes that program and then enters the **same Parser/runtime
instance**, preserving bindings, functions, imports and host state. If initial execution
fails, Nift returns the failure and does **not** enter the REPL. This avoids turning a failed
noninteractive program into an accidental interactive session.

`--` terminates Nift execution-option parsing. Everything after it is a user argument, even
if it begins with `-`. Once a file source has been selected, remaining tokens are also script
arguments except for the deliberately supported pre-source execution options; scripts should
use `--` when an argument would otherwise be ambiguous with one of those options. `-e`/`-c`
consume exactly the following token as source text; later tokens are user arguments (with an
optional `--` separator).

The standalone bindings are immutable host-owned values with this contract:

| Invocation | `cmd` | `args` |
|---|---|---|
| `nift script.f` | `script.f` (the invocation spelling, not canonicalised) | `[]` |
| `nift ./script.f a b` | `./script.f` | `["a", "b"]` |
| executable `./script.f a` with `#!/usr/bin/env nift` | script-path spelling supplied by the OS/env launcher | `["a"]` |
| `nift -e '...' a` | `<command-line>` | `["a"]` |
| `nift -c '...' a` | `<command-line>` | `["a"]` |
| `printf '...' | nift - a` | `<stdin>` | `["a"]` |
| `nift - < script.f` | `<stdin>` | `[]` |
| plain `nift` / `nift -i` | `<repl>` | `[]` |
| `nift -i script.f a` after initial execution | remains the file spelling | remains `["a"]` |
| `nift -i -e '...' a` after initial execution | remains `<command-line>` | remains `["a"]` |

`cmd` is therefore argv[0]-**style script identity**, matching the Strut `cmd`/`args`
shape without exposing Nift's own process argv as the script command. Imports share their
caller's `cmd` and `args`; they do not manufacture a module-local argv.

Execution options that affect capability/host setup (`--no-process`, `--fs-root=...`) are
parsed by Nift and are never inserted into `args` unless they occur after `--`. Their exact
accepted placement is kept intentionally narrow and covered by black-box tests.

Diagnostics use stable logical source names: the invocation spelling for real files,
`<command-line>` for `-e`/`-c`, `<stdin>` for stdin programs, and `<repl>` for interactive
statements. No temporary filename is exposed as public identity.

### CP9 — platform contract

- [x] Define the target vocabulary and ownership model before adding flags.
- [x] `platform()` means selected output/execution platform, not host OS and not CPU
  architecture.
- [x] Define the default target when no explicit target is selected (normally a
  stable host/native value) and how it behaves in scripts, templates, builds and
  embedded contexts.
- [x] Define target scoping: per CLI invocation/build/runtime, never an accidental
  mutable process-global that leaks between concurrent embedded Engines.
- [x] Specify how package code queries target and how unknown/custom targets are
  handled.
- [x] Commit the contract before implementation.

**Frozen target contract (2026-09-27):**

1. **Meaning.** `platform()` returns the selected output/execution platform for the
   current Nift evaluation. It is deliberately orthogonal to `os()` (the host
   operating system) and `arch()` (the host CPU architecture). Cross-targeting
   must never change the values returned by `os()` or `arch()`.
2. **Default.** With no target selection, `platform()` is exactly `"native"`.
   `native` means "the current host/default execution target"; it does not alias
   itself to `linux`, `macos` or `windows`. This gives package code a stable way
   to distinguish ordinary native operation from an explicitly selected platform.
3. **Built-in target IDs.** The initially reserved built-ins are `native`,
   `linux`, `macos`, `windows`, `android`, `ios` and `wasm`. These are lowercase
   stable API strings. Selection uses the explicit `--platform=<id>` form; do not add convenience flags such as bare `--android`.
4. **Custom target IDs.** Extensible/package-defined targets are allowed through
   the canonical `--platform=<id>` form. IDs are normalized by requiring lowercase
   ASCII and must match `[a-z0-9][a-z0-9._-]*`; Nift does not silently lowercase,
   rewrite or reinterpret an invalid spelling. A syntactically valid unknown ID
   is retained verbatim so package/tooling ecosystems can define targets without
   waiting for a Nift core release.
5. **Query model.** Scripts, templates, imported package/module code and in-process
   build hooks all query the same invocation-owned value through `platform()`.
   Package code should compare the returned string and provide its own fallback
   or controlled error when it does not support that target. Merely selecting a
   custom target does not make core Nift reject it as unsupported.
6. **CLI/build scope.** Target state belongs to one top-level CLI invocation (and
   to the build/runtime objects created by that invocation). A nested parser,
   import, template render or in-process hook inherits that value explicitly.
   It is never stored in a mutable process-global or environment variable as the
   source of truth. Sequential invocations in one process must return to
   `native` unless a new target is explicitly supplied.
7. **Embedded scope.** The embedding API will own a per-Engine default target of
   `native`, with a per-render/per-execution context override where concurrent
   calls need different targets. Each Parser receives an immutable target value
   from its owning host/context. Two Engines, or two concurrent contexts on one
   Engine, must be able to use different targets without cross-talk.
8. **External children.** Nift does not implicitly mutate the process environment
   to communicate target selection to arbitrary child processes. A child process
   is a separate invocation and receives a target only when the caller passes it
   explicitly. Nift-managed in-process hooks are not children and do inherit the
   current target as described above.
9. **Multiple selections.** A CLI invocation may select at most one target.
   Repeating the same target or combining target selectors is an error rather
   than "last one wins". Host/target compatibility checks belong to the feature
   consuming the target (for example a future native-app backend), not to the
   string-selection mechanism itself.
10. **Diagnostics/API stability.** `platform()` takes no arguments. Platform IDs are
    API values suitable for package branching and tests, so changing the meaning
    or spelling of a reserved built-in ID requires an explicit compatibility
    decision rather than an incidental CLI refactor.

**CP9 completion (2026-09-27):** the target contract above is frozen before any
implementation. CP10 is responsible for the data-driven CLI selectors and the
first `platform()` plumbing; CP9 intentionally changes no runtime behavior.

## Phase E — native concurrency language/runtime

### CP15 — concurrency memory/ownership contract

- [x] Freeze which Nift values are copied, shared or prohibited when crossing a
  thread/async boundary.
- [x] Define mutation/data-race rules for arrays, maps, sets, structs, closures,
  streams, files, command/process objects and host/FFI values.
- [x] Decide whether ordinary mutable values are thread-confined by default and
  require explicit synchronized/shared wrappers, or whether another equally
  enforceable model is superior.
- [x] Define exception/error propagation, cancellation/lifetime and join behavior.
- [x] Define closure capture semantics for named functions and lambdas crossing
  threads.
- [x] Do not expose APIs until the model can be tested and explained.
- [x] Commit the concurrency design and adversarial test plan.


#### Frozen concurrency boundary (CP15)

1. A spawned `thread(...)` or `async(...)` owns an isolated Parser execution context. The parent Parser is never concurrently entered by a worker.
2. Ordinary transferable values (`null`, booleans, numbers, strings, arrays and objects containing only transferable values) cross the boundary by deep value copy. Worker mutation therefore cannot race the parent.
3. Opaque/resource markers (files, streams, commands/processes, collection/struct instance handles, page references and future FFI/host handles) are not implicitly transferable. Passing one is a runtime error until that type has an explicit thread-safe contract.
4. Named functions and lambdas use the existing callable representation. Their executable definition and lexical value environment are snapshotted for the worker; captured ordinary values are deep-copied. A closure does not gain shared-reference semantics merely because it is run on another thread.
5. A thread handle and, from CP17, synchronization/shared-state handles are the intentional cross-thread opaque handles. Their internal C++ state is thread-safe and lifetime-owned independently of lexical scope until joined/released.
6. `join()` is single-result deterministic: success returns the callable result; a worker runtime error is rethrown/reported by the joining Parser; repeated join returns the same completed result/error rather than executing twice.
7. Destroying a live thread handle must not call `std::terminate`. The runtime owns completion state; Parser/script shutdown joins outstanding owned threads before teardown. A future detach feature would require a separate lifetime contract and is not part of v4.5.
8. Worker exceptions never cross a C++ thread boundary directly. They are converted to Nift error state and observed at join/await.
9. Cancellation is not promised by the initial primitive. Shutdown is cooperative by join; CP18 may add bounded-pool shutdown semantics without inventing unsafe forced thread termination.
10. Mutable shared state is opt-in only. CP17 may expose an explicit shared/synchronized container/handle; ordinary arrays/maps/structs remain copied. Mutexes do not retroactively make arbitrary parent Parser internals shareable.
11. Host operations invoked from workers are permitted only where the host seam is documented thread-safe. Existing immutable/read-only host data may be read concurrently; process-global side effects such as stdout/environment remain protected by their existing runtime locks or are documented separately.
12. `thread`/`async` APIs must reject non-transferable graphs recursively, including a transferable-looking array/object that contains an opaque marker.

Adversarial certification includes: nested workers, many short workers, result/error replay, parent scope exit before join, closure snapshots, rejected resource graphs, shutdown with live workers, separate Parser/runtime concurrency, and TSan where the environment supports it.

**CP15 completion (2026-09-27):** the copy-by-default/isolate-the-Parser model above is frozen. This deliberately trades implicit shared-reference convenience for an enforceable no-data-race default; explicit synchronized sharing belongs to CP17.

## Release-level success criteria

Nift v4.5.0 is ready for release only when all of the following are true:

- plain `nift` is a stable persistent shell/REPL;
- direct file invocation is the only normal file-run command (`nift file.f`),
  with `nift run` and `nift sh` removed;
- `-e`, `-c`, `-i`, stdin source and executable shebang scripts have coherent,
  tested semantics;
- `cmd` and `args` are stable and documented;
- environment plus `os()`/`platform()` introspection is coherent and platform state
  is isolated correctly;
- interactive background jobs and job control are real, race-tested and honest
  about platform limits;
- threads/mutexes and async/await execute real parallel work under a documented
  shared-state model and survive TSan/adversarial testing;
- C ABI FFI works on supported release platforms with explicit ownership/lifetime
  rules and deterministic fixture tests;
- the existing embedding engine is promoted into a supported scripting +
  templating runtime with host values/functions, isolated instances and
  concurrency/lifetime certification;
- source tests, independent regression suite, embedding/binding conformance,
  sanitizers, performance/RSS gates, website build and cross-platform CI are all
  green from committed state;
- every completed checkpoint is committed, every repository is clean, and no Git
  repository was corrupted, replaced, force-reset or otherwise borked during the
  campaign.
