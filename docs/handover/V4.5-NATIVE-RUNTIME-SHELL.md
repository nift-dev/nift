# Nift v4.5.0 — native runtime, concurrency, FFI and shell campaign

Status: **planned / not yet implemented**. This document is the authoritative
step-by-step campaign plan for Nift v4.5.0. It starts from the v4.4.0 release plus
the existing `Begin v4.5.0 development` checkpoint and deliberately turns the
Nift language/runtime into a more complete general-purpose scripting environment
without weakening the website-generation/build guarantees that already exist.

The campaign has four primary goals:

1. make Nift a first-class scripting language and interactive shell rather than
   requiring `nift run` / `nift sh` wrapper commands;
2. add real native concurrency: threads, mutexes and `async` / `await` backed by
   actual parallel execution;
3. add a practical native FFI with a stable, testable ownership/type boundary;
4. harden and promote the existing experimental embedding work into a supported
   embeddable Nift scripting/template runtime.

A fifth cross-cutting goal is to finish the intentionally deferred Bash-style job
control story from v4.4 and make platform/target awareness good enough for future
native/mobile/application work.

## Settled v4.5 product decisions

These decisions are accepted unless implementation evidence proves that one is
unsafe or internally contradictory. Do not repeatedly reopen them during the
campaign.

- Remove `nift run <path>` outright. There are no compatibility users to protect.
  `nift <path>` is the script-file invocation syntax.
- Remove `nift sh` outright. Plain `nift` starts the persistent interactive Nift
  shell/REPL.
- CLI dispatch is command-first, then file-path fallback. A known Nift command
  remains a command. Otherwise, if the first positional argument names an
  existing regular file, execute it as a Nift script. If it is neither, fail
  explicitly with an error that says the command is unknown **and** the path does
  not exist. Do not silently reinterpret typos.
- Keep direct shebang execution. It already exists in the v4.5 baseline and must
  be certified rather than reimplemented: `#!/usr/bin/env nift` followed by an
  executable `.f` file must continue to work.
- Named user functions are already first-class callable values in the baseline.
  Preserve and certify them through concurrency/FFI/embedding work rather than
  implementing a second callable mechanism.
- Scripts use `cmd` and `args`, following the Strut convention rather than
  `argc`/`argv`: `cmd` represents the invocation command (`argv[0]` semantics;
  not necessarily a canonical path) and `args` contains only user arguments.
  The existing immutable `args` script binding remains the foundation.
- Keep `getenv`, `setenv` and `unsetenv`; they already exist. Add `env()` if the
  cross-platform implementation can return a safe ordinary Nift map/object of
  the current process environment.
- Add `os()` and `target()`. `os()` describes the host operating system. `target()`
  describes the selected build/runtime target and is deliberately distinct from
  the host. Example intended direction: `nift build --android` selects target
  `android`, and `target()` evaluates to `"android"` while the build executes.
- Prefer `target()` over a vague `platform()` API. Add `arch()` separately if
  architecture introspection is useful; do not overload `target()` with CPU
  architecture.
- Support stdin as source: piped source and explicit `nift -`, including
  `nift - < script.f`.
- Add conventional inline-code/interactive flags. `-e` is the canonical execute
  spelling; `-c` is an accepted alias. `-i` means remain interactive after the
  supplied file/stdin/inline source executes, preserving the live runtime state.
- Finish real Bash-style job control: background jobs, `jobs`, `fg`, `bg`,
  process groups, terminal handoff, signal handling and `wait` semantics where
  supported by the host OS. Do not fake job control on platforms whose process
  model cannot implement a claimed behavior.
- `async` / `await` must be genuinely parallel-capable. Do not implement a
  JavaScript-style single-threaded event-loop substitute and call it
  multithreading.
- Native `thread` / `mutex` APIs and `async` / `await` must share one coherent
  concurrency/runtime ownership model rather than becoming two unrelated
  schedulers.
- FFI initially targets the C ABI. Cross-platform dynamic libraries are `.so`,
  `.dylib` and `.dll`; richer C++ ABI binding is not a v4.5 requirement.
- The existing `include/nift/`, `src/embed/`, C ABI and language-binding work is
  the starting point for embedding. Reuse and harden it; do not create a second
  embedded runtime beside it.
- The supported embedding story must include both Nift scripting and Nift
  template/rendering use cases. Host applications must be able to inject values,
  expose native functions, execute/evaluate Nift, and receive values/errors back
  without shelling out to the CLI.
- Preserve the v4.4 security/capability distinction. Build safety, `--no-process`,
  filesystem restrictions and embedded-host boundaries must remain explicit.
- Do not add new third-party runtime dependencies casually. Prefer the C++
  standard library, OS APIs and existing Nift-owned/runtime code; any new
  vendored dependency requires deliberate approval and release/distribution
  analysis first.

## Current baseline facts to preserve

The campaign starts from code, not assumptions. The following are already present
in the current checkout and should be treated as compatibility evidence:

- `nift <existing-file>` shorthand already dispatches to script execution.
- a leading shebang is already stripped from script source before evaluation;
- standalone scripts already receive immutable `args` containing user arguments
  only;
- named functions already evaluate to first-class callable values alongside
  lambdas;
- `getenv`, `setenv` and `unsetenv` already exist in script land;
- v4.4 already has foreground TTY handoff, direct process spawning, pipelines,
  redirection, `&&` / `||`, history, completion and process restrictions;
- background `&`, `jobs`, `fg` and `bg` are deliberately not implemented yet;
- an experimental C++ Engine, Context API, C ABI and Go/Python/Node/C# binding
  work already exist under `include/nift/`, `src/embed/` and `bindings/`;
- the existing embedded Engine already has substantial concurrency, reload,
  project-awareness and conformance testing that must not regress;
- the ordinary Nift CLI build is intentionally kept independent of embedding-only
  implementation objects.

Before changing any of these surfaces, read the relevant existing handovers,
especially `V4.4-EXECUTION-SHELL-PACKAGES.md`, `EMBED.md`, `EMBED-ROADMAP.md`,
`INTEGRATION-PLAN.md`, `NIFT-BINDINGS-PROGRAMME.md`, `TESTING.md`,
`DEVELOPMENT.md`, `DECISIONS.md` and `RELEASES.md`.

## Repository-safety and checkpoint rules

These rules apply to **every checkpoint** in this campaign.

- Start each checkpoint from clean working trees in every repository that will be
  touched. Record branch names and `git status --short --branch` before editing.
- Never use destructive Git operations (`reset --hard`, forced checkout over
  unknown work, history rewriting, deleting `.git`, replacing repositories with
  exported copies, or broad cleanup commands) as part of normal checkpoint work.
- Never initialize a new repository inside an existing repository or accidentally
  nest/copy `.git` metadata.
- Do not move or rewrite unrelated files merely to make a diff look clean.
- Preserve existing user/maintainer work. If the checkout is unexpectedly dirty,
  investigate and stop that checkpoint rather than discarding changes.
- Keep changes checkpoint-sized and reviewable. A checkpoint may span the Nift
  source repo, the independent `nift-regression-suite`, and the website repo when
  the public behavior requires all three, but each repository must have its own
  coherent commit.
- Run the checkpoint's focused tests before committing. Run the broader maintained
  wall appropriate to the risk before declaring the checkpoint complete.
- Inspect `git diff --check`, `git diff`, staged diff, and final `git status` in
  every changed repository.
- **Commit at the end of every completed checkpoint.** Do not begin the next
  checkpoint with uncommitted implementation/docs/test work from the previous
  one. If multiple repositories changed, commit all of them before advancing.
- Record the resulting commit IDs in this campaign document as checkpoints are
  completed. The handover itself is living project state, not a detached diary.
- No autonomous push, tag, release, package publication or history rewrite.
  Follow the established release handover and stop for the maintainer at the
  explicit publication gates.
- Keep source tests and the independent regression suite independent enough to
  catch shared mistaken assumptions.
- Add a regression test for every bug found during implementation, review, CI or
  dogfooding before considering the bug fixed.
- Cross-platform claims require Linux/macOS/Windows evidence. Platform-specific
  functionality may be explicitly scoped, but must fail honestly rather than
  pretend parity.

## Definition of done for a public-behavior checkpoint

A checkpoint that changes public behavior is not complete until all applicable
items below are done:

- implementation is complete and locally reviewed;
- focused source tests cover success, failure and edge cases;
- affected maintained source-test runners/Make targets include the new tests;
- black-box coverage is added to `nift-regression-suite` and wired into
  `run-contract.sh` when the behavior is externally observable;
- `nift-dev.github.io` source documentation, command reference, examples,
  navigation and AI-facing discovery material are updated where relevant;
- the documentation website builds successfully with the exact candidate Nift
  binary when the changed feature affects site build/runtime examples;
- stale syntax/command names are searched globally across source, tests, docs,
  examples and handovers;
- `git diff --check` and appropriate sanitizer/concurrency/platform tests pass;
- changed repositories are committed and clean.

## Release-level success criteria

Nift v4.5.0 is ready for release only when all of the following are true:

- plain `nift` is a stable persistent shell/REPL;
- direct file invocation is the only normal file-run command (`nift file.f`),
  with `nift run` and `nift sh` removed;
- `-e`, `-c`, `-i`, stdin source and executable shebang scripts have coherent,
  tested semantics;
- `cmd` and `args` are stable and documented;
- environment plus `os()`/`target()` introspection is coherent and target state
  is isolated correctly;
- interactive background jobs and job control are real, race-tested and honest
  about platform limits;
- threads/mutexes and async/await execute real parallel work under a documented
  shared-state model and survive TSan/adversarial testing;
- C ABI FFI works on supported release platforms with explicit ownership/lifetime
  rules and deterministic fixture tests;
- the existing embedding engine is promoted into a supported scripting +
  templating runtime with host values/functions, isolated instances and
  concurrency/lifetime certification;
- source tests, independent regression suite, embedding/binding conformance,
  sanitizers, performance/RSS gates, website build and cross-platform CI are all
  green from committed state;
- every completed checkpoint is committed, every repository is clean, and no Git
  repository was corrupted, replaced, force-reset or otherwise borked during the
  campaign.
