## Load generator

`bombardier v2.0.2` on the load node. Settings per run:
`-d <dur>s -c <conn> -a (disable keep-alive) -l -p r -t 30s`.
Both backends close connections after each response (`Connection: close`), so
`-a` keeps connection behaviour equivalent. Median of 3 measured runs per
tuple after a 5 s warmup; results below are the median req/s, p50, p95 (ms).

## One application, both backends

Identical `app.template.f`; only `http.use_backend("BACKEND")` differs.
Routes: `/text` (tiny), `/json/:id`, `/query?q=...`, `/echo-small` (1 KiB POST),
`/echo-large` (64 KiB POST), `/large` (128 KiB response), `/compute` (CPU).

Configs measured:
`native` (max_concurrency 16), `process_default` (conc 1, oneshot),
`process_conc4` (conc 4, oneshot, pool 4),
`process_persistent` (conc 4, persistent, pool 4).
The process servers were health-checked (must serve 2xx) before measuring; the
first benchmark run's process numbers were invalid (flaky launches) and were
re-measured with the health-check harness.

## Ratios (native = 1.0)

At c=4 (a representative concurrent load), native vs process_persistent:

| wl | req/s ratio | p50 ratio |
|---|---|---|
| A_text | 0.025 (6.1 vs 243.7) | 1.9x worse |
| B_json | 0.025 | 1.9x |
| C_query | 0.024 | 2.0x |
| D_echo1k | 0.022 | 2.0x |
| E_echo64k | 0.023 | 2.0x |
| F_large | 0.006 (0.5 vs 87.9) | 2.0x |

Native is ~25x lower throughput and ~2x higher latency at c=4 than a healthy
persistent-worker process backend. Even the literal process default (conc=1) is
~6x faster in throughput.

## Process-tree RSS and CPU

Idle parent RSS is ~8 MB for both. During load (whole process tree):

| config | peak RSS | peak CPU |
|---|---|---|
| native | 830 MB (F_large c=16) | ~92% |
| process_default | 432 MB | ~90% |
| process_conc4 | 479 MB | ~93% |
| process_persistent | 487 MB | ~93% |

Native's 830 MB peak occurs only on the 128 KiB-response handler at c=16,
driven by Nift string-concatenation building the response body (the same
handler drives the process peaks to ~430-490 MB). Typical workloads keep native
RSS well below that (A_text samples ~16-36 MB).

## Startup

Not separately timed; both backends were listening within ~1 s of launch.
Process backend pays one-time worker/helper startup on first request.

## Concurrency / head-of-line blocking

Dedicated `/fast` + `/slow` (4M-iteration CPU handler) app:

| backend | /fast alone p50 | /fast p50 with /slow in background |
|---|---|---|
| native | 182 ms | 704 ms (~4x degradation) |
| process | 23-26 ms | 25-27 ms (no degradation) |

Native's single-threaded event loop is blocked by the slow handler, stalling
unrelated fast requests ~4x. The process backend's worker pool isolates the
slow handler and shows no head-of-line blocking. Also, under a sustained
CPU-handler load the native loop saturates and the listen backlog overflows
(connection refusals); the process backend degrades more gracefully.

## Adversarial / resource behaviour

- **slowloris (60 partial connections):** native good-client latency degrades
  to ~17 s p50 (the loop is consumed polling the partial connections);
  process rejects excess admissions (5xx) while good clients stay responsive
  (~81 ms).
- **early-disconnect / malformed floods:** both survive; native fd count grows
  transiently then recovers.
- **slow readers on /large:** native buffers each 128 KiB response per
  connection, RSS spikes to ~229 MB for 20 slow readers and the native server
  process died during the test (post-attack connections refused). The process
  backend kept serving.

Native does not yet hold up under adversarial slow-client load; the process
backend does. This is the single most serious blocker for native-as-sole-backend.

## Feature-parity matrix

| Capability | process | native | Needed before Python removal? |
|---|---|---|---|
| routing | yes | yes | - |
| route params | yes | yes | - |
| query | yes | yes | - |
| text | yes | yes | - |
| JSON | yes | yes | - |
| bytes | yes | yes | - |
| cookies | yes | yes | - |
| forms | yes | no | required |
| files | yes | no | required |
| ranges | yes | no | required |
| multipart | yes | no | required |
| uploads | yes | no | required |
| spooled request bodies | yes | no | implementation detail (native can use in-memory) |
| streaming | yes | no | required |
| concurrency/admission | yes (pool) | partial (max_concurrency) | required (HOL mitigation) |
| handler fault isolation | yes (workers) | partial (recoverable errors; fatal kills loop) | required |
| request limits | yes | yes | - |
| timeouts | yes | client-read only | required (response/send/admission) |
| graceful shutdown | yes | partial (max_requests) | required |
| observability/status | yes | no | useful |

Not a native defect: persistent Python worker protocol, exchange-directory
protocol, helper lifecycle — these are process-backend implementation details
that would disappear with the helper, not features native must reproduce.

## Recommendation: **KEEP TEMPORARILY**

Native is not yet competitively usable as the sole backend:

1. **Throughput/latency:** ~25x lower throughput and ~2x higher latency than a
   healthy persistent process backend at c=4; flat ~5 req/s regardless of
   concurrency. The dominant cause is the fixed 50 ms event-loop poll plus
   per-request connection close in a single thread.
2. **Head-of-line blocking:** a slow handler stalls unrelated requests ~4x.
3. **Adversarial:** slowloris stalls good clients; slow readers can spike RSS
   and kill the server.
4. **Feature gaps:** forms, files, ranges, multipart, uploads, streaming,
   observability, full timeouts/shutdown, fault isolation.

None of these are architectural dead ends — the poll interval, send/pending
state machine, bounded parser, and package-facade architecture are sound. The
gaps map to the existing staged plan. If native's event loop is retuned
(shorter poll, keep-alive-ready design) and the required parity lands, the
process backend can be retired; until then it must stay.

## Proposed remaining checkpoints (adjusted for these findings)

```
SERVER3  forms/cookies/request parsing parity; poll-interval + event-loop tuning
SERVER4  files/ranges/multipart/uploads/spooled bodies
SERVER5  concurrency/admission/fault isolation (worker-less, loop-hardening)
SERVER6  streaming
SERVER7  graceful shutdown/observability/hardening (slowloris/slow-reader caps,
         per-connection response buffering limits)
SERVER8  full parity + differential + adversarial certification
SERVER9  native sole backend; delete helper/http_helper.py and process machinery
```

## Integrity notes

- Same app, same payloads, same load generator, same connection semantics
  (`Connection: close` both sides) for every comparison.
- Process configs health-checked (2xx) before measurement; the invalid first
  run was discarded and re-measured.
- Process-tree RSS/CPU accounted across the whole tree (parent + helper +
  workers), not a single PID.
- F_large c>=32 and G_compute rows were error-flood artifacts (2xx=0,
  connection refusals) and were excluded from the tables.
