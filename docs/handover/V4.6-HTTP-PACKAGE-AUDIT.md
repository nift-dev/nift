# v4.6 HTTP package audit (investigative)

Status: audit-only checkpoint. No production/package code changed.

This document audits the current Nift HTTP situation and the curl-backed
replacement path. It corrects the common assumption that the Nift `http`
package is an HTTP client: **`http` is an HTTP server**, and the client lives
in the separate `curl` package. Both currently use subprocess backends
(Python helper for the server; the `curl` executable for the client); neither
uses libcurl via FFI.

## 1. Current architecture

```text
http package (SERVER)          curl package (CLIENT)
    http.f (facade/routing)        curl.f (facade)
        |  subprocess                  |  subprocess (argv, no shell)
        v                              v
    helper/http_helper.py          curl executable on PATH
        |  Python stdlib only           |  libcurl inside curl (user's build)
        v                              v
    HTTP/1.1 server socket          HTTP client
```

- `http` package (`nift-packages/http`): backend-neutral server facade. Only
  `process` backend implemented; `ffi`/`native` reserved but unimplemented
  (`src/http.f:70-85`). Owns routing, response builders, worker protocol.
- Python helper (`helper/http_helper.py`, 2030 lines, Python **stdlib only**):
  owns the listening socket, HTTP/1.1 parsing, finite wire limits, worker
  lifecycle, response serialization, file/range transfer, chunked streaming,
  admission and shutdown (`PROTOCOL.md:9-13`).
- `curl` package (`nift-packages/curl`): HTTP **client** facade. Only `process`
  backend implemented; `ffi`/`native` reserved (`src/curl.f:39-54`). Drives the
  `curl` executable via Nift's structured argv `run()` (`src/curl.f:228`).
- No shared code, no dependency between the two packages; neither manifest
  declares `dependencies` (`http/manifest.json`, `curl/manifest.json`).

## 2. Current HTTP API (public surface)

Server (`http` facade, `src/http.f`):

```text
http.server(config)                                  -> server handle
http.get/post/put/patch/delete/head(app, path, fn)   -> register route
http.route(app, method, path, fn)
http.text/json/cookie/file/file_from/stream(...)     -> response builders
http.listen(app)                                     -> run the server (blocks)
http.save_upload(upload, dest) / http.save_body(...) -> consume spooled bytes
http.server_backend(app), backends(), backend(),
   use_backend(name), capabilities(), available()
```

Client (`curl` facade, `src/curl.f`):

```text
curl.request(url, opts?)                             -> response object
curl.get/post/put/patch/delete/head(url, opts?)
curl.backends(), backend(), use_backend(), capabilities(),
   version(), features(), available()
```

Response shape (`curl/README.md:19-31`): `ok` (true for any HTTP response,
including 4xx/5xx; false only on transfer/backend failure), `status`,
`headers` (every value an array), `body` (buffered text or null), `output`,
`error`, `error_code`, `backend`, `exit_code`.

Options (`curl/README.md:34-43`): `method`, `headers`, `body`, `json`,
`timeout` (curl `--max-time`), `follow_redirects` (`-L`), `output`.

Important reality check: the client API `http.get(url)` / `http.post(url)`
**does not exist**. `http.get(app, path, handler)` is server route
registration. The names the user recalled for a client are occupied by server
semantics in the `http` package. This is a naming/scoping collision that must
be resolved before building a client facade called `http` (see section 15).

## 3. Python-helper protocol and dependency

- Invocation: `run(python3, helper.py, --host, --port, --nift, --app <cmd>,
  --cwd, ... 29 limit flags)` (`src/http.f:545-584`), Nift argv API, no shell.
- `python3` resolved from `$NIFT_HTTP_PYTHON` override else `which("python3")`
  (`src/http.f:26-30`); the Nift executable from `$NIFT_HTTP_NIFT` else
  `which("nift")` (`src/http.f:32-36`). Disabled under `NIFT_NO_PROCESS`.
- Worker bridge: env `NIFT_HTTP_WORKER=1|persistent`,
  `NIFT_HTTP_REQUEST=<request.json>`, `NIFT_HTTP_RESPONSE=<response.json>`
  (oneshot), plus `NIFT_HTTP_READY` for persistent (`http_helper.py:707-711,
  828-832`). Persistent workers additionally read newline-delimited
  exchange-directory paths on stdin (`PROTOCOL.md:25-31`).
- Framing: protocol-1 JSON envelopes, compact
  (`json.dump(ensure_ascii=False, separators=(",",":"))`); worker writes
  `response.tmp` then atomic `move()` to `response.json` (`src/http.f:426-432`).
  Headers lowercase → arrays. Binary request bodies never cross JSON framing;
  they are opaque package-owned spool tokens (`{"kind":"spooled",...}` /
  `{"kind":"upload",...}`) consumed by `save_body`/`save_upload`.
- Exit-code handling: helper exits 2 on fatal error
  (`http_helper.py:2028-2030`); worker timeout → 504, launch failure/nonzero
  exit/bad response metadata → 500, overload → 503, malformed wire → bounded
  4xx/501, client disconnect → 499.
- Timeout behavior: `worker_timeout_ms`, `client_timeout_ms`,
  `response_timeout_ms`, `shutdown_grace_ms`, `admission_timeout_ms`
  (`src/http.f:514-540`).
- Failure behavior: helper returns structured `{"ok":false,"error_code":...}`
  results; application 4xx/5xx responses are serialized normally (not package
  errors).
- Python modules: `argparse, email.message, email.utils, json, os, re, select,
  shutil, signal, socket, stat, subprocess, sys, tempfile, threading, time,
  urllib.parse` — **stdlib only**, no third-party packages
  (`http_helper.py:4-20`).

## 4. curl-package architecture and API

- Mechanism: `args = ["-sS", ...headers, -H "k: v"]`; JSON body →
  `--data-binary @<temp>` + `-H Content-Type: application/json`; string body →
  `--data-binary @<temp>`; `-X <method>`; `-L`; `--max-time <s>`; `-w
  %{http_code}`; `-D <header_temp>`; `-o <output>` or `-o <body_temp>`; `--`;
  then URL (`src/curl.f:174-227`). Executed as `run("curl", ...args)` —
  structured argv, never shell concatenation.
- Temp-file lifecycle: `$TMPDIR/$TEMP/$TMP/pwd`; `mktemp` preferred, PowerShell
  fallback on Windows, checked package-local fallback with a documented small
  TOCTOU race (`src/curl.f:72-100`, `README.md:103-107`). All temp files
  removed on every path.
- Error mapping: nonzero exit → `ok:false`, `error_code` `28`→`timeout`,
  `23`/`26`→`file_error`, else `transport_failure` (`src/curl.f:230-239`).
  Missing curl → `backend_unavailable`, exit 127.
- Header parsing: resets on each `http/` block so only the final response
  survives redirects; repeated names (e.g. `set-cookie`) become arrays; all
  values normalized to arrays (`src/curl.f:113-146`).
- libcurl via FFI: none. The package shells to the `curl` executable; the
  comment at `src/curl.f:5-7` states Nift carries no libcurl/TLS dependency.
- Binary handling: `response.body` is read via `open(body_temp)` into a string
  (text-oriented); arbitrary bytes are supported through the `output` option
  (`README.md:110-113`).

## 6. Can Python be removed completely?

**Direct answer: qualified. For the client, Python is already absent. For the
server, Python cannot be removed without a Nift-native HTTP server.**

- The **client** never involved Python. The Python helper is exclusively the
  **server** backend. The user's goal of "no Python helper, no Python runtime
  dependency for Nift HTTP" applies to the server, and libcurl **cannot** serve
  HTTP — it is a client library. A Python-free server therefore means a
  Nift-native HTTP/1.1 server (socket + parsing + worker lifecycle + streaming
  + multipart), which is a large core/native campaign far beyond this
  checkpoint, not an FFI wrapper.
- If the goal is a production-grade **client**, the clean path needs zero core
  changes and zero Python: extend the `curl` package and layer a client facade
  on it (section 7).
- The server's Python helper is certified by 16 package-local harnesses and
  should be treated as a separate decision track (keep-and-document, or later
  native-server campaign), not silently removed.

## 7. Recommended layering (client)

```text
http client facade (ergonomic request/response/session API)
    |
    |  @import("curl")  [declared dependency, Batch 5 graph]
    v
curl package (low-level but process-safe primitives over the curl executable)
    |
    |  run("curl", ...)  argv, no shell
    v
curl executable -> user's libcurl (TLS/HTTP/2/3 as built)
```

This is achievable **now**, with **no Nift core modification**:

- Batch 5 transitive dependencies make `http -> curl` a first-class package
  dependency. This would be the first real transitive dependency in the
  nift-packages org (currently all 21 packages are leaves; the only
  `dependencies` entry in the wild is sqlite's dirty self-referential artifact
  — do not use that as a model). Declare
  `{"dependencies":{"curl":{"source":"curl","ref":"latest"}}}` (or a pinned
  git source/commit; `docs/packages/README.md:4-8`).
- `http` knows the Nift-level curl API; `curl` alone knows curl-CLI details;
  libcurl internals never leak into `http`. This preserves the package
  export/private boundary without touching core.
- The reserved `ffi`/`native` backends stay reserved; they are not required.

## 8. FFI blockers for a direct `curl -> libcurl FFI` client

Direct libcurl FFI is **blocked** by the current FFI. The exact, source-cited
mismatches:

| Desired libcurl call | Current Nift FFI | Exact mismatch | Core change required |
| --- | --- | --- | --- |
| `curl_easy_setopt(CURL*, CURLoption, ...)` (variadic) | fixed arity only, `ffi_prep_cif` (`src/ParserExpression.cpp:1511`); grammar rejects a second `(` (`:1480`); `ffi_prep_cif_var` absent repo-wide | variadic call unsupported | variadic FFI support |
| `size_t (*)(char*, size_t, size_t, void*)` write/header/read callbacks | only `i64(i64)` callback (`src/ParserExpression.cpp:1473-1474`; `ParserScript.cpp:268-276`), integer result only | signature shape + `size_t` return | general callback signatures |
| callback needs a `user_data`/closure context pointer | trampoline is a bare 1-arg function pointer reading thread-local state (`src/ParserExpression.cpp:76-84`); no way to identify which buffer/session | no context pointer | callback context/userdata |
| callbacks retained across `curl_easy_perform` | callbacks valid only synchronously within the enclosing `ffi_call` (`src/ParserExpression.cpp:86-117`); foreign-thread entry returns sentinel | retained callback unsupported | retained callbacks |
| `curl_slist` linked list (headers) | `ptr` is opaque; `ffi_struct` rejects pointer fields (`src/ParserExpression.cpp:1470`) | no list traversal/construction | list/pointer-field structs |
| `curl_multi`/`curl_ws_*` | no multi API, no websocket tokens | n/a | (blocked by the above) |

There is no single tiny missing primitive; the smallest coherent core change is
"general callback signatures with a closure context pointer" (which also
requires variadic `curl_easy_setopt`). That is substantial FFI work with its
own safety surface. The **package-level workaround that avoids all of it** is
to keep the curl-executable subprocess backend and add features via curl CLI
flags (section 5). Recommendation: do **not** do FFI work for this checkpoint;
extend the process backend instead.

## 9. Sessions / auth / cookies design options

For the subprocess client, a session is **package-managed state**, not a live
libcurl handle:

- Recommended: `session := http.session({base_url, headers, cookie_jar_file,
  timeout, follow_redirects, auth})`; per-request curl processes reuse the
  session's headers and `-b <jar> -c <jar>` for persistent cookies.
- Trade-offs vs libcurl handle reuse: per-request processes are trivially
  concurrency-safe (no shared handle), give up HTTP keepalive/connection reuse
  (each curl exits), and are simpler and dependency-free. A long-lived session
  process could retain keepalive but adds worker lifecycle complexity and
  is not recommended initially.
- Auth: Basic via `-u user:pass` or `-H Authorization: Basic ...`; Bearer via
  `-H Authorization: Bearer <token>`; arbitrary `Authorization` via headers.
- Cookie jar: file-based (`-b`/`-c`) persists across requests/processes and
  across program runs; an in-memory jar is a package-managed map when the
  file-free mode is wanted.
- Redirect policy: `follow_redirects` boolean today; add `max_redirects`
  (`--max-redirs`).
- Default timeout and base-URL joining live in the session facade.

Correctness/concurrency/keepalive trade-off table:

| Property | per-request processes (recommended) | one curl easy handle | libcurl share/multi |
| --- | --- | --- | --- |
| correctness | high (independent) | high | high |
| concurrency | safe | unsafe (handle not thread-safe) | multi-managed |
| connection reuse | none | keepalive within one handle | best |
| cookie persistence | file jar | in-handle | share handle |
| implementation complexity | low | blocked by FFI | blocked by FFI |
| thread safety | safe | not safe | multi |

## 10. Multipart / forms / uploads / downloads

All achievable at package level via curl CLI flags (zero core changes):

- multipart: `-F field=value`, `-F field=@file;type=...` with boundary handled
  by curl.
- forms: `--data-urlencode name=value` / `--data name=value`.
- uploads: `-T file` (PUT upload) / `--upload-file`.
- downloads: `-o <path>` already present; add `--create-dirs`, `--continue-at -`.
- binary-safe bodies: use the certified Nift `bytes` type (CP17-CP19:
  `open_bytes`, `bytes(array)`, `write(bytes)`, `write_bytes`, strict UTF-8
  `decode`) for `response.body`/uploads instead of string reads. No package
  consumes `bytes` yet; the http/curl packages predate it and still say "no
  general byte value" (`http/README.md:166-170`) — that claim is stale.

## 11. Streaming / SSE / WebSocket assessment

- Buffered HTTP: works today.
- Streaming response body: for a subprocess client, `--no-buffer` writes to
  stdout; the package would need to read the child's output incrementally. Nift
  `run()` is buffered (`Process.cpp`), so incremental reads require either a
  process-stream primitive or deferral. Streamed **uploads** via `-T`/`-F @-`
  are simpler and can use `--limit-rate`.
- SSE: an incremental line parser over a streamed body. Feasible as a package
  feature once streaming reads exist; do not promise in HTTP0-HTTP2.
- WebSockets: the `curl` **CLI** does not expose websockets; libcurl
  `curl_ws_send/recv` requires the multi interface and callbacks, both blocked
  by FFI (section 8). **Recommendation: WebSockets remain a later
  package/checkpoint** — consistent with the acceptance that we do not force
  everything into the first HTTP rewrite.

## 12. Async strategy

- Current client is synchronous `run()` per request.
- Recommended initial: **wrap synchronous requests in Nift async/thread
  tasks** — `async () => curl.get(url)` / `thread(() => ...)`. Nift has
  threads, async functions/futures/await, mutexes and atomics
  (`src/ParserExpression.cpp:1223-1235, 1390-1413, 1417-1423, 1840-1856`);
  handles (threads/FFI/timers) are non-transferable across workers, so a
  per-request model fits cleanly.
- libcurl multi interface: only after FFI grows (section 8). Correctness and
  simple async composition first; multi sophistication later.

## 13. Error model after Batch 4

Recommended mapping (matches the user's proposed model and the existing
package conventions):

- **HTTP status 4xx/5xx** = successful transport: `ok:true`, `status`,
  `response.ok == false` only if we later add a convenience boolean at the
  facade layer; keep `status` authoritative.
- **DNS / connect / TLS / timeout / redirect / malformed-URL failures** =
  package-defined request failure: `ok:false`, stable `error_code`
  (`timeout`, `transport_failure`, `file_error`, `backend_unavailable`),
  human `error`, `exit_code` as diagnostic only.
- Do **not** convert these into language-catchable Errors. The package
  convention (and the Batch 4 recoverable policy) keeps package/process
  failures as structured results, not catchable runtime Errors. `ffi.library_
  load_failed`/`ffi.symbol_not_found` and import failures are the recoverable
  core errors; transport failures from a spawned process stay command-level.
- Body-callback / local-file failures: `file_error`.

## 14. Platform / distribution considerations

- **Client (curl executable)**: preinstalled on GitHub-hosted runners
  (ubuntu/macos/windows), Windows ships `curl.exe` (10+), macOS ships
  `/usr/bin/curl`. No workflow installs or checks it; the package degrades to
  `backend_unavailable` when absent. Lowest deployment burden; no dynamic
  linking, no SONAME/DLL discovery.
- **libcurl FFI** (not recommended now) would require per-platform discovery:
  Linux SONAME (`libcurl.so.4`), macOS system/homebrew, Windows DLL. That is a
  real distribution burden the subprocess approach avoids.
- **Server (Python)**: requires `python3` at runtime (stdlib only). GitHub
  runners install it (setup-python on the Windows job); a production deploy
  needs Python present. This is the server's deployment dependency.
- Android: out of scope for this checkpoint; nothing in the client path is
  Android-specific either way.

## 15. Compatibility / migration risks

- **Naming collision (highest-risk)**: the `http` package name is a **server**
  API (`http.get(app, path, handler)`). A client facade called `http` would
  collide. Options to decide in HTTP0:
  1. Keep `http` = server; build the client as a new facade/package (e.g.
     `httpc`/`client`/extend `curl` with a higher-level API).
  2. Rename server route verbs (breaking; 16 harnesses + docs).
  3. Add a client sub-facade (`http.client.*`).
  The audit recommendation is option 1 or 3 — do not break the certified
  server API.
- `curl` package's bare aliases (`request/get/post/...`) are already flagged
  deprecated (`curl/README.md:51-53`); keep the `curl` facade.
- Existing tests must keep passing: `http/tests/*` (16 Python harnesses,
  package-local, not in core CI) and `curl/tests/dogfood.py` plus core
  `test-v44-packages` combined dogfood.
- First real transitive dependency: `http -> curl` will be the first graph edge
  in nift-packages; it should be pinned to an exact commit and exercised
  through `nift packages`/`nift install` before advertising `latest`.
- Binary body semantics change (string → bytes) is a behavioral change for
  `response.body`; keep `output`-mode stable and add bytes under an opt-in or
  a new field.

## 16. Recommended checkpoint plan (reality-adjusted)

The original HTTP0-HTTP9 sequence assumed a client rewrite of `http`. Given the
audit (server vs client split), the revised plan:

```text
HTTP0  audit + architecture freeze (this document)
      - decide naming: client facade vs server http name (section 15)
HTTP1  make the client a first-class consumer: declare http -> curl
      dependency (first real Batch 5 graph edge), pin exact commit
HTTP2  extend curl package: multipart (-F), forms (--data-urlencode),
      uploads (-T), downloads (-o/--create-dirs), auth (-u/Authorization),
      cookies (-b/-c), TLS (--cacert/--cert), proxy (-x), --max-redirs,
      --connect-timeout, HTTP/2 --http2; add timing/effective-url fields
HTTP3  binary-safe bodies via the bytes type (response.body + uploads)
HTTP4  sessions/cookies/connection-state facade on top of curl
HTTP5  downloads/uploads/binary/streaming (streamed upload first; streamed
      download/SSE once a process-stream read primitive exists or deferred)
HTTP6  async integration (thread/async-wrapped synchronous client)
HTTP7  SSE decision (package-level incremental parser)
HTTP8  WebSocket decision: DEFER (curl CLI has none; libcurl WS blocked by FFI)
HTTP9  cross-platform/adversarial/performance certification
SERVER  separate track: keep + document the Python helper, or a later
       Nift-native HTTP server campaign (large). Not part of the client plan.
```

Highest-risk implementation areas: the naming decision (section 15), the first
real transitive dependency (HTTP1), binary-body semantics (HTTP3), and any
streaming-read primitive (HTTP5).

## Conclusion

- The **client** can become "no Python, curl-package-backed, zero core
  changes" immediately: `http (client facade) -> curl -> curl executable`.
- The **server** cannot use libcurl (client-only library); removing Python
  from the server means a Nift-native server campaign — separate and large.
- Direct libcurl FFI is blocked by exact FFI gaps (variadics, callback
  signatures, closure context, retained callbacks, slist); do not attempt it
  in this checkpoint.
- WebSockets should remain a later checkpoint.
- Everything client-side is achievable at package level with the existing
  curl-executable backend plus the certified `bytes` type.
