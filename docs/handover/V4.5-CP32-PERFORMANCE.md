# Nift v4.5 CP32 performance and resource evidence

Date: 2026-09-27. Candidate: `Nift v4.5.0` after CP31. These numbers are local Linux/container observations and are **not** cross-machine release thresholds. The reproducible driver is `benchmarks/v45_runtime_perf.py`.

## Results

| Measure | Local result |
| --- | ---: |
| `nift -e 'return 1;'` median startup (15 runs) | 2.064 ms |
| inline startup max RSS | 4,328 KiB |
| trivial direct-file max RSS | 4,404 KiB |
| immediately-exited REPL max RSS | 3,528 KiB |
| 100 native thread create+join operations | 56.67 ms |
| 100 async submit+await operations | 53.29 ms |
| 20,000 mutex-protected increments / 4 workers | 7,337.85 ms |
| 5,000 scalar FFI calls | 966.02 ms |
| embedded Engine create+destroy | 508 ns/op |
| repeated embedded `execute` on one Engine | 50,532 ns/op |
| execution spread across eight Engines | 61,056 ns/op |
| direct C++ representative render | 119,248 ns/render |
| public C ABI representative render | 119,516 ns/render (+0.2%) |
| full v4.5 integration dogfood | 0.28 s, 12,928 KiB max RSS |

## CP1 comparison

CP1's deliberately rough `-O0` smoke observations were approximately 4.1 MiB RSS for a trivial direct script and 3.4 MiB for an immediately-exited REPL. The current optimized candidate measured ~4.3 MiB and ~3.4 MiB respectively in the same environment class. That does not indicate a material idle/startup memory regression from adding concurrency, FFI and embedding; importantly, FFI libraries and async workers are not initialized merely by starting an ordinary script.

CP1 did not preserve stable release-grade timing thresholds, so this checkpoint does not invent percentage regressions against incomparable `-O0` observations. The values above establish the reproducible v4.5 release-candidate baseline.

## Interpretation

- Native thread and async one-at-a-time lifecycle costs are in the same ~0.5 ms/op class in this deliberately simple end-to-end CLI fixture.
- The mutex fixture is intentionally pathological: four interpreter workers repeatedly acquire a scripting-level mutex and perform `get` + `set` on every increment. It is a contention/locking stress measurement, not a recommendation for fine-grained numeric loops. Batching work outside the critical section remains the correct usage pattern.
- FFI scalar calls cross parsing/type-validation/ABI dispatch on every invocation; the low-level interface is designed for native integration, not as a substitute for vectorizing hot numeric loops in native code.
- Reusing one embedded Engine is materially cheaper than process startup and avoids reinitializing runtime state. Eight isolated Engines remain in the same order of magnitude per execute.
- Existing C ABI render overhead remains effectively negligible in this fixture (+0.2%).

No performance result here justified a product-code rollback or architectural change. Cross-platform and longer-running benchmark comparisons remain part of Codex/hosted review rather than being inferred from one container.

## Reproduce

```bash
python3 benchmarks/v45_runtime_perf.py --json-out /tmp/v45-runtime-perf.json
make benchmark-c-abi
/usr/bin/time -f '%M KiB' ./nift -e 'return 1;'
```
