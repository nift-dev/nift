C++ EXCEPTION PATH IN THE SHELL LOOP (handover obligation): REPRODUCED
Nothing above the shell-loop lambda has a handler: there is none in
run_script_shell_loop, run_cli or main, and no terminate handler. With GCC,
an exception that finds no handler calls std::terminate without unwinding.
So neither cleanup domain runs: the JobTable destructor does not run either,
contrary to the review's assumption.

Reproduced with no fault injection, on the integrated binary, in both legacy
(NIFT_VM=0) and VM-session (NIFT_VM unset) mode:
  - Steps: open a managed file with unsaved changes; start a background job
    (sleep N &); mkdir gone; cd gone; rmdir ../gone.
  - shell_prompt_text() then calls the throwing fs::current_path(). It throws
    filesystem_error, which escapes the loop.
  - The process aborts with exit status 134 ("terminate called after throwing
    an instance of std::filesystem::filesystem_error").
  - The "managed file left open" diagnostic is lost, and the rest of the
    input is never executed.
  - On Linux the background job still dies, but only through the kernel:
    Host stages default to die_with_parent (PR_SET_PDEATHSIG SIGKILL). No
    such backstop exists on macOS.
  - Inherited, not introduced by CP19: the same call is in v4.12.0 and in
    the foundation.
  - Other exception sources reaching the loop (std::bad_alloc) take the same
    path. Both std::stoi calls in the job and exit builtins are already
    guarded.

Smallest correction: proposed, NOT applied, for owner review.
  1. Trigger: shell_prompt_text() uses fs::current_path(std::error_code&). A
     deleted working directory then shows "?".
  2. Backstop: in run_script_shell_loop, `status = loop()` goes inside
     try/catch. On an exception it prints "internal error: <what>", uses
     status 70 and falls through to the existing post-loop cleanup.
Prototype in a scratch copy, then deleted:
  - Backstop alone: exit 70, the internal error and the managed-file
    diagnostic; both domains settle.
  - Both changes: the shell continues, and at EOF it settles normally.
  - test-cp19-cleanup-cli passes 72 x 2 on the corrected build.
Affected tests: add an "exception" lane to tests/runtime2/cp19/cleanup_cli.py
(deleted working directory), asserting no abort, both diagnostics, nonzero
status and that the job is gone.
